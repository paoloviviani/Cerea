# Configuration

!!! info "For operators"

    Every environment variable the chat understands, by feature. The repository's `.env` is the defaults file; a test fails if it lists a variable the code does not read, or the code reads one it does not list.

Cerea reads its settings from the environment; the repository's `.env` lists
every variable the app understands, with its comments and its default. A value
exported into the environment, or set in `.env.local`, wins over `.env`.

In a deployment you rarely set these by hand: the deploy kit's `.env.example` is
the deployment's own commented list, and `./configure --set KEY=VALUE` changes a
single one (see [Deploying](deploy.md)). Switches take the string `true` or
`false`; the defaults below say which way an unset one goes.

## The variables that choose your deployment shape

Three variables decide what kind of deployment you are
running, before any of the fork's variables below matter:

| Variable              | What it decides                                                                                                                                                                                                                                                                                                                                                             |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OPENAI_BASE_URL`     | Where inference goes: a Pystino gateway's `/v1`, or any OpenAI-compatible endpoint. **No default**: empty, the chat refuses to start. The kit sets it to the bundled gateway (`http://gateway:8000/v1`, or `CHAT_OPENAI_BASE_URL`).                                                                                                                                         |
| `USE_USER_TOKEN`      | Names the mode (below). `true` is **Pystino mode**: users sign in through the gateway and every inference call carries their own token, so quotas and the ledger are theirs. Unset or `false` is **standalone mode**: one shared `OPENAI_API_KEY` and no per-user billing. A hand-built chat pointed at Pystino without `true` silently bills everything to the shared key. |
| `OPENID_PROVIDER_URL` | The identity provider users sign in with. **No default**: empty, sign-in has no issuer to talk to (set it with `OPENID_CLIENT_ID`); the kit sets it from `OIDC_ISSUER`. The computer agent's issuer (`CODE_MACHINE_ISSUER`) defaults to it.                                                                                                                                 |

### Two modes, never a mix

The chat reaches models in exactly one of two ways, decided by `USE_USER_TOKEN`
(no other setting names the mode):

|                  | **Pystino mode** (`USE_USER_TOKEN=true`)                                        | **Standalone mode** (unset or not `true`) |
| ---------------- | ------------------------------------------------------------------------------- | ----------------------------------------- |
| Credential       | each user's own sign-in token, only                                             | one shared `OPENAI_API_KEY`, only         |
| Endpoints        | the gateway at `OPENAI_BASE_URL`, for every model, including `MODELS` overrides | one OpenAI-compatible endpoint            |
| `OPENAI_API_KEY` | must be empty                                                                   | the shared key                            |
| Boot catalogue   | fetched with no key, then filtered per user and billing group                   | fetched with the shared key               |

A mix either bypasses the gateway's per-user access, billing and redaction,
or hides models users are entitled to, so **the chat refuses to start** on
one, and the error names the setting to change:

- `OPENAI_API_KEY` set while `USE_USER_TOKEN=true`:
  empty it, or set `USE_USER_TOKEN=false` for a standalone endpoint.
- In Pystino mode, a `MODELS` entry whose `endpoints` name a `baseURL` other
  than `OPENAI_BASE_URL` (an endpoint with no `baseURL` counts: it defaults to
  `api.openai.com`), or carry their own `apiKey`: remove `endpoints` from that
  entry. Overrides that only set flags such as `supportsArtifacts` are fine.
- `USE_USER_TOKEN=true` with no `OPENAI_BASE_URL`: there is no gateway to
  present tokens to.

An install from before this rule that mixed the two fails to start after
upgrading until one of those is changed. With the deploy kit, run
`./configure`: it reports the mix and offers the fix. It can only write one
mode: the `generic` preset writes a shared key with personal tokens off, every
other preset writes no key.

The [Deploying](deploy.md) page shows the two complete variable sets, for a
chat against Pystino and for a chat against any other endpoint.

| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| `OPENID_SCOPES`             | The scopes the chat asks the identity provider for, separated by spaces. The default is upstream's (HuggingChat's); the deploy kit writes `openid profile email groups`, less any scope the issuer's discovery document does not list, for an IdP that answers `invalid_scope` to `groups`. Keep it equal to the gateway's `GATEWAY_OIDC__SCOPES`. | `OPENID_OFFLINE_ACCESS`     | `off` stops the sign-in asking for the `offline_access` scope, which is what gets the refresh token behind [scheduled chats](chat-admin.md#scheduled-chats) and background token refresh. The kit passes it as `OIDC_CHAT_OFFLINE_ACCESS`                                                                                                                                                                                                                                                                                                      |
| `OPENID_LOGOUT_URL`         | The provider's logout page, for one that publishes no `end_session_endpoint` (the bundled Authelia: `<issuer>/logout?rd={redirect}`). `{redirect}` is where to land. | `ADMIN_CLI_LOGIN`           | Default `false`. `true` prints a one-time admin login URL (with a token) in the server log at boot and lets a signed-in user who presents it become chat admin. It is always off when OpenID is configured, whatever this says; the kit sets it `false`. Admin rights come from the identity provider                                                                                                                                                                                                                                                                                                        |
| `LOGOUT_ALSO_CLEAR_COOKIES` | Other applications' session cookies on this origin to expire when someone signs out, `name` or `name:path`, comma-separated. On the Pystino stack: `gw_session,gw_idt:/auth`, so signing out of one never leaves the other in                                                                                                                                                                                                                                                                                                                                                                                |
| `CHAT_MIGRATE_ISSUER_FROM`  | When moving to a new identity provider: the old issuer. A first login that finds no account takes over the old account with the same verified email                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `PUBLIC_TURIN_PHRASES`      | Rotating Turin-dialect greetings printed beside the logo on a new chat, one per page load, comma-separated. `false` or empty restores the plain name                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## Secrets shared with the gateway

| Variable             | What                                                                                                                                                                                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CHAT_SECRET_KEY`    | Encrypts connector credentials at rest (AES-256-GCM). There is **no default**: without it connectors stop working, and nothing stores a plaintext token. Rotate it and stored connector credentials no longer decrypt                                             |
| `CHAT_ERASURE_TOKEN` | The gateway's own credential for the chat's `/internal/erasure` (deleting a user everywhere). Minted by `./configure`, sent over the compose network only, compared in constant time. The chat also refuses any `/internal/*` request that carries a proxy header |

## Notifications

| Variable                 | What                                                                                                                                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CHAT_VAPID_PUBLIC_KEY`  | The public half of the deployment's Web Push key pair (base64url, 65 bytes). Minted once by `./configure`. Browsers subscribe against it, so replacing it strands every subscription. Unset means push is off ([Notifications](notifications.md)) |

## Images

The assistant's `generate_image` tool draws with a gateway model of
`kind: image` (`POST /v1/images/generations`), as the signed-in user: metered
per image with their token, with their model access groups and bill-to.

```ini
CHAT_IMAGE_MODEL=flux-2-klein-4b
```

Which model: the administrator's choice under Administration → Assistant →
Images, else `CHAT_IMAGE_MODEL`, else the first `kind: image` model the user may
use. The tool and the composer's "Create an image" item are offered only to a
user for whom a model resolves; the catalogue is asked with a two-second
deadline and a slow or failing gateway means no tool, not a slow page. Whether
each generation asks first is the "Ask before generating images" switch on the
same screen (no environment variable). See [Images](chat-admin.md#images).

## Transcription

Audio is transcribed by a gateway model of `kind: transcription`
(`POST /v1/audio/transcriptions`), as the signed-in user: it is metered per
audio minute with their token, their model access groups and bill-to. The
gateway refuses files over 25 MB. Two features use it:

- **Audio attachments** are transcribed once, at upload, and the transcript is
  kept beside the file (never re-transcribed per turn). Audio attachments may be up to
  25 MB (about 25 minutes of ordinary audio); every other attachment stays at 10 MB.
  The app's `BODY_SIZE_LIMIT` is 40 MB to carry them.
- **Dictation** with the microphone, when Administration → Assistant → Voice &
  audio is set to "Transcription model".

Which model: the administrator's choice under Administration → Assistant →
Voice & audio (it works whether or not knowledge bases are enabled), else
`CHAT_TRANSCRIPTION_MODEL`, else the first `kind: transcription` model the user
may use. A choice saved on the Knowledge screen by the one release that kept it
there is still read until one is saved on the new screen. Audio is not screened
by the gateway's redaction.

**Deprecated direct endpoint.** `TRANSCRIPTION_BASE_URL` with
`TRANSCRIPTION_MODEL` sends dictation straight to
`${TRANSCRIPTION_BASE_URL}/${TRANSCRIPTION_MODEL}` with the **deployment's own
key** (`OPENAI_API_KEY`, or the user's token only when `USE_USER_TOKEN` is
`true`), not through the gateway and not metered per user. While the pair is
set it keeps serving dictation even when `CHAT_TRANSCRIPTION_MODEL` or a model
chosen in the admin screen exists; those apply to audio attachments, which never
use the direct endpoint. One deprecation line is logged. Remove the pair to send
dictation through the gateway as the user.

What the old `CHAT_DICTATION` words do (unchanged from before):

| `CHAT_DICTATION`   | pair unset     | pair set                                 |

an old value with the pair set as "Transcription model".
