# Thin machine agent: architecture and wire protocol (v1)

Status: implemented (P0 and parity milestones 1–9, 2026-09-24; live since the deploy-rearch cutover). This is the `/code` data path (ADR 0089, which supersedes 0085).
Source of truth for both implementations: the Go agent, galopin (this repository's `agent/`, moved from Pystino `deploy/agent/` with its history preserved), and Cerea's machine link (`src/lib/server/code/machine*.ts`).

The move and rename left this protocol itself untouched on purpose — live
machines depend on it: the subprotocol (`pystino-machine.v1`, §3), the WSS
path (`/api/v2/code/machine`), the `X-Pystino-Machine-*` headers (§3) and
the `opencode-enrollment` OIDC client id all keep their names below. Only
the binary, its log prefixes, its on-disk state directory and its packaging
are galopin now; nothing on the wire changed.

## 1. Shape

```
 browser ──HTTPS (existing /api/v2/code/* REST + SSE)──► Cerea server
                                                          ▲
                                   WSS, dialled OUT by the machine, bearer = enrollment access token
                                                          │
 user's machine:  galopin run
                   ├─ link      : WSS client to Cerea, reconnect w/ backoff, token renewal frames
                   ├─ sessions  : backend-agnostic materializer (epoch/seq, ring buffer, auto-accept, policy)
                   ├─ backend   : Backend interface; first impl = opencode (supervises `opencode serve`)
                   └─ shim      : the existing /v1 proxy (injects the gateway bearer + x-bill-to), now with a local secret + Host allowlist
                                   opencode ──HTTP──► shim ──HTTPS──► Pystino /v1
```

- **One binary** (`galopin`, grown from `pystino-enroll` by way of `pystino-agent`), no Node/npm/Python on the machine besides opencode itself.
- **One credential root**: the enrollment's OIDC refresh token. The same access token authenticates the WSS to Cerea and the `/v1` calls. Revoking at the IdP kills both within one access-token lifetime.
- **Nothing capability-bearing is stored in Cerea.** Cerea holds only a live socket that the machine opened. A DB dump yields device names and ids, nothing that can reach a machine.
- LLM traffic never crosses Cerea (unchanged two-path rule).

## 2. Why this backend interface, and not ACP as the interface

We checked `opencode serve` (1.18.31, OpenAPI at `GET /doc`) against ACP (Agent Client Protocol).

- `opencode serve` gives, over HTTP + one SSE stream (`GET /global/event`, all directories): sessions (`POST/GET/PATCH/DELETE /session`), async prompt (`POST /session/:id/prompt_async`, `parts[]` with text and file parts, per-prompt `agent` = mode and `model`), abort, permissions (`permission.asked` event, `POST /permission/:id/reply {reply: once|always|reject}`), questions, modes (`GET /agent`, `mode: primary`), models (`GET /config/providers`), per-session diffs (`GET /session/:id/diff`, `session.diff` event), children (subagents, `GET /session/:id/children`), todos, usage (tokens and cost on assistant messages / step-finish parts), compaction (`POST /session/:id/summarize`), revert, worktrees (`/experimental/worktree`), basic auth (`OPENCODE_SERVER_PASSWORD`). Sessions persist across restarts.
- ACP (JSON-RPC over stdio) covers the core: `session/new|load|prompt|cancel|set_mode|set_model`, `session/update` notifications (message/thought chunks, tool_call(+update), plan, mode updates), `session/request_permission` with allow/reject once/always options, image/resource content blocks. It lacks (or has only unstable drafts for) session listing, usage/context, diffs, subagent trees and multi-client attach; the client owns the process.

**Decision:** our own backend interface, _shaped like ACP_ (same nouns: session, prompt, update stream, permission request with once/always/reject, cancel, mode, model) plus optional capabilities for what ACP lacks (usage, diff, children, compact, worktrees). opencode is implemented over `opencode serve` (richer than `opencode acp`, survives restarts, multi-directory). The generic **ACP adapter** is the natural _second_ backend (covers Gemini CLI, Claude Code and Codex via their ACP adapters, Pi via `pi-acp`); it simply reports fewer capabilities. Capabilities are advertised per backend in `hello`, and Cerea hides affordances a backend lacks.

`galopin run --backend acp --acp-command "<cmd…>"` (default `opencode acp`) runs the generic adapter (`internal/backend/acp`) instead of the default `opencode` backend; `--backend opencode` (or omitting the flag) keeps the default. The adapter spawns and supervises `<cmd…>` (restart with backoff, process group + `Pdeathsig`, same discipline as opencode's own supervisor) and speaks JSON-RPC 2.0 newline-delimited over its stdio. `initialize` (no fs/terminal client capabilities) seeds `ID()`/`Version()` (`acp:<agentInfo.name>`) and `Capabilities()` (Images from `promptCapabilities.image`; Diff/Children/Usage/Compact/Worktrees always false, since ACP has no wire message for any of them; AutoAccept always true — the materializer's job, not a backend capability). Prompts map to `session/prompt`'s content blocks and return once sent (the async contract); the turn's completion arrives later as a `status` event once the response carries `stopReason` (`cancelled` → idle; `refusal`/an RPC error → `error`). `session/update` notifications become the normalized event stream, with ids derived from a local turn counter rather than the agent's own per-chunk ids, so "one message per turn per role" holds regardless of how a given agent chunks its output. `session/request_permission` becomes `permission.asked`; `ReplyPermission` answers with the `optionId` of kind `allow_once`/`allow_always`/`reject_once` (with fallbacks); a `Cancel` with a permission pending answers it `{outcome:{outcome:"cancelled"}}` first. `session.rename`/`session.delete` are best effort (a title overlay; `session/close` if advertised); `session.setModel` (the still-unstable `session/set_model`) reports the agent's error cleanly if unsupported. Verified live against opencode 1.18.31's `opencode acp` (see `acp_it_test.go`), including the one spot it diverges from the published ACP schema: `session/new` answers with a bespoke `configOptions` list rather than `modes`/`models` — both shapes are read.

## 3. Transport and authentication

- Endpoint: `GET wss://<cerea-origin>/api/v2/code/machine` (WebSocket upgrade), subprotocol `pystino-machine.v1`.
- Headers: `Authorization: Bearer <access token>`, `X-Pystino-Machine-Id: <uuid>` (generated once, persisted in the agent state dir; a re-enroll mints a new one), `X-Pystino-Machine-Name: <display name>`.
- Cerea validates the JWT **locally** (JWKS from the issuer's discovery doc, cached): `iss` == configured issuer (`OPENID_PROVIDER_URL`, exact, trailing-slash-normalized); `aud` contains `CODE_MACHINE_AUDIENCE` (default `pystino-api`); `azp` (or `client_id`) == `CODE_MACHINE_CLIENT_ID` (default `opencode-enrollment`); `exp` in the future; `typ` header, if present, is not an ID token. Userinfo is never used. This is review C1 done properly for the one thing a machine presents.
- The token's `sub` must map to an existing Cerea user (same mapping the OIDC login uses). No user → close `4403 "sign in to Cerea once before connecting a machine"`.
- Handshake rejections happen **before** the upgrade completes when possible (HTTP 401/403), otherwise as close codes:
  `4401` token invalid/expired · `4403` forbidden (revoked device, unknown user) · `4409` a newer connection for the same machine replaced this one · `4000` protocol error.
- **Token renewal:** the agent refreshes its access token at ~70% of lifetime and sends `{"type":"auth","token":"…"}`. Cerea re-validates (same `sub`, same checks) and moves the connection's deadline. Cerea closes with `4401` when `exp + 60s` passes without renewal. That makes IdP-side revocation effective within one access-token lifetime.
- Keepalive: WebSocket ping every 20 s from Cerea; the agent treats 60 s of silence as dead and reconnects. Agent reconnect: exponential backoff 1 s → 30 s with jitter, never gives up except on `4403`.
- **Deadlines everywhere (R1):** the dial has a 10 s timeout; every Cerea→machine request has a deadline (default 15 s, `session.sync` 20 s). An offline machine answers "offline" instantly from the registry, never hangs.

## 4. Pairing and authorization (per user, per device, revocable)

- A machine connecting with a valid token and an unknown `machineId` creates a `codeDevices` row `{userId, machineId, name, status: "pending", sub, iss, createdAt}` (unique index `(userId, machineId)`). The socket stays open but **no operations are forwarded** until the owner confirms.
- The `/code` panel lists pending machines with **Confirm / Reject**. Confirm → `status: "paired"` and Cerea sends `{"type":"status","status":"paired"}` down the socket. This click is the fresh human approval review C2 asks for; a phished device-code approval alone never reaches the panel's operations.
- Revoke (DELETE device) → row becomes `status: "revoked"` (tombstone keyed by machineId), the live socket is closed with `4403`, and further connects with that machineId are refused. Re-enrolling mints a new machineId → a new pending row.
- Every browser request is authorized as: `locals.user` present (C6) → device row with `userId == locals.user._id` and `status == "paired"` → the live connection for that row is authenticated as the same `sub`. A device can never be driven by a user other than the one whose credential the machine holds (C10 closed by construction; there is no paste flow).
- **Machine-side policy (the machine's veto, C4):** `galopin` has a local policy file (`policy.json` in its config dir, set by `enroll` flags, never writable over the link):
  - `autoAccept`: `"allowed" | "denied"` (default `denied`). When denied, the agent refuses `session.setAutoAccept` and never auto-replies to permissions whatever Cerea sends.
  - `workspaceRoots`: absolute paths; if non-empty, `workspace.create` outside them is refused.
  - `allowFreeModels`: bool (default false). When false the agent lists and accepts only gateway (`pystino/*`) models; Cerea filters as well (defence in depth).
  - Machine powers (ADR 0090, §9; specified, not built yet; they exist only when `hello.machine.capabilities` says so):
    - `files`: `"read" | "off"` (default `"read"`; `enroll --no-files`). `off` answers every `files.*` op `forbidden`.
    - `fileWrite`: `"allowed" | "denied"` (default `denied`; `enroll --allow-file-write`). Gates `files.write`.
    - `fileDeny`: glob list (default: the §9.4 list; `enroll --file-deny GLOB` adds, `--no-default-file-deny` drops the defaults). Matching entries are listed with `redacted: true`, reading them is `forbidden`, and search skips them.
    - `terminal`: `"allowed" | "denied"` (default `denied`; `enroll --allow-terminal`). Gates every `terminal.*` op.
    - `maxTerminals`: int (default 8). `terminal.open` beyond it is `invalid`; a terminal kept around only for exit-retention display does not count against it.
    - `commandShell`: `"allowed" | "denied"` (default `denied`; `enroll --allow-command-shell`). Gates `session.command` (§6): while denied, a command whose template expands `` !`…` `` shell — and every command whose shell fact is _unknown_ (an MCP prompt, an ACP command), because nobody has seen a template to scan — is refused `forbidden`. The expansion runs inside opencode before any permission rule is asked, so it is off until an owner explicitly opts in.
    - `agentTools`: `"allowed" | "denied"` (default `allowed`; `enroll --no-agent-tools`, and `galopin policy set --no-agent-tools` to tighten later). The one power that is on by default: `session_spawn`/`session_send` add nothing without a per-call approval, waived only for a session already auto-accepting and only where it cannot escalate (§6 "Auto-approval"); spawned sessions never inherit auto-accept and are never more permissive than their spawner. `denied` installs **no** galopin tool into the backend (`OPENCODE_CONFIG_DIR` is not set by galopin) and the backend reports `agentTools:false`; `steer` is unaffected (it is about a person's own mid-turn prompts and is reported from the backend alone). Takes effect at the next `run`. Older machines omit the field.
    - `projectConfig`: `"allowed" | "denied"` (default `denied`; `enroll --allow-project-config` opens it, `galopin policy set --no-project-config` tightens later). Denied starts `opencode serve` with `OPENCODE_DISABLE_PROJECT_CONFIG=1 --pure`: a workspace's `opencode.json`, `.opencode/` commands/agents/MCP and `AGENTS.md`/`CLAUDE.md` are not loaded (known gap, 1.18.32: a repo's `.opencode/plugin(s)` scripts still run). Allowed loads them and pins the gateway config over the repo's as `OPENCODE_CONFIG_CONTENT` (provider, `enabled_providers`, `model`, `small_model`); a repo setting any routing key is audited as `project_config.override_attempt {keys}`. `workspace.list` entries carry `projectConfigIgnored: true` when the machine denies and the repo carries such config. Older machines omit the field and load project config.
    - `backgroundSubagents`: `"allowed" | "denied"` (default `denied`; `enroll --allow-background-subagents` opens it, `galopin policy set --no-background-subagents` tightens later). Allowed starts `opencode serve` with `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=1`, so the task tool accepts `background:true`: the child keeps running after its parent turn ends and its result is injected back as a synthetic `<task>` message the panel folds into a visible parent marker. Denied never sets the flag (any inherited value is stripped), so `background:true` fails closed inside opencode. Takes effect at the next `run`. Older machines omit the field, read as denied.
    - A local `galopin policy set` may only tighten these; loosening needs `enroll`.
  - The policy is reported in `hello` so the UI can explain refusals.

What this achieves: no capability at rest in Cerea; per-device, per-user authority that ends on revoke (socket closed, machineId tombstoned) or on IdP revocation (≤ one token lifetime); the machine can veto auto-accept and confine workspaces. What it does **not** achieve: while a machine is connected and paired, a compromised Cerea process can still send prompts to it within the machine's policy (the panel is, by design, a remote control). Mitigations beyond that (per-prompt signing by the browser) are out of scope for v1.

JSON text frames, one object per frame, `type` discriminates.

| M→C               | `{"type":"res","id":"<same>","ok":true,"result":{…}}` or `{"type":"res","id":"…","ok":false,"error":{"code":"not_found"\|"invalid"\|"forbidden"\|"unavailable"\|"backend"\|"unsupported","message":"…"}}`                                                                                                                                                                                                                                                                    |
| M→C               | `{"type":"event","sessionId":"…","epoch":"…","seq":123,"rootSessionId":"…","event":Event}` — pushed for **every** session of the machine; Cerea fans out to watchers of the session and of its root, and drops the rest. `rootSessionId` is the top-level ancestor (the session itself for a top-level session); a child session's envelopes therefore reach its root's watchers mid-turn, which is what surfaces subagent approvals and questions in the parent's view (§7) |
| M→C               | `{"type":"credential","state":"ok"\|"expiring"\|"expired","detail":"…"}` — the gateway/enrollment credential's health (replaces regex-matching `lastError`, review C9). `expired` = refresh got `invalid_grant`; the machine sends it before its socket dies so Cerea can record it on the device row and show the re-enroll card                                                                                                                                            |
| M→C               | `{"type":"auth","token":"…"}` (renewal, §3)                                                                                                                                                                                                                                                                                                                                                                                                                                  |

Unknown frame types and unknown event kinds are ignored by both sides (forward compatibility); unknown ops answer `unsupported`.

`Backend = {"id":"opencode","version":"1.18.32","capabilities":{"diff":true,"children":true,"usage":true,"compact":true,"images":true,"files":true,"worktrees":false,"autoAccept":true,"questions":true,"revert":true,"revertFiles":true,"efforts":true,"commands":false,"toolImages":true,"agentTools":true,"steer":true}}` — `commands` is probed, never versioned: opencode advertises it only when its own `GET /doc` lists the `session.command` operation (cached per process, re-probed after a supervised restart); ACP reports it always, its `available_commands_update` carrying the list per session. `toolImages` means tool parts list the images their calls produced and `session.attachment` (§6) serves them: opencode and ACP both report it; a machine older than this field omits it, and Cerea then renders no tool images. `agentTools` means galopin has installed its own agent-coordination tools into the backend (§6, "Agent tools"): opencode reports it, ACP never does. `steer` means a `session.prompt` sent while the session's turn is running is accepted and folded into the running turn rather than refused (opencode: `prompt_async` queues it server-side; ACP refuses it, §6 `session.prompt`); a machine older than either field omits it, read as `false`.
`Policy = {"autoAccept":"denied","workspaceRoots":[],"allowFreeModels":false}`

With the machine powers (§9), `hello` also carries `"machine":Machine`, and `Policy` gains the power fields:
`Policy = {…, "files":"read", "fileWrite":"denied", "fileDeny":[…], "terminal":"denied", "maxTerminals":8}`
`Machine = {"capabilities":{"files":true,"fileSearch":true,"fileWatch":false,"fileWrite":true,"terminal":true}}`: a capability means "this galopin implements it on this OS", and the policy means "the owner allows it"; both must hold. `terminal` is false on non-Unix builds. Two more frame shapes exist only there: `notice` (§9.5) and binary terminal frames (§9.2). Two more error codes: `"conflict"` (`files.write` revision mismatch, `error.details = {revision}`) and `"too_large"` (over a cap).

**Worktrees.** `workspace.create`'s `worktree` form runs `git worktree add -b <branch> <path> <base|HEAD>` against the workspace named by `from`, using the git CLI directly rather than opencode's experimental `/experimental/worktree` — worktrees are a property of the checkout, not of one backend. `path` is `<repo parent>/<repo name>.worktrees/<branch>` (`git rev-parse --show-toplevel` finds the repo root regardless of whether `from` points at the root or a subdirectory); `branch` is refused if it contains `".."` or is otherwise unsafe as a path component. The resulting directory is registered as an ordinary workspace, still subject to `workspaceRoots`, carrying `{worktreeOf: from, branch}`. `workspace.archive`'s `removeWorktree` runs `git worktree remove` (`--force` when `force` is set); git itself refuses a dirty worktree without `force`, so there is no separate dirty check. Archiving without `removeWorktree` just hides the workspace, same as any other — the directory and the git worktree both remain on disk.

**Agent tools (capability `agentTools`).** Three tools galopin installs into opencode itself — `session_list`, `session_spawn`, `session_send` — so the model of one session can coordinate with other sessions **on the same machine**. They are _tools the model calls_, not new `req.op`s: Cerea sends nothing new, and what it sees is ordinary session, message and permission traffic carrying the fields below. (They are opencode custom tools, one file each in a directory galopin owns and passes as `OPENCODE_CONFIG_DIR`; a tool's `execute(args, ctx)` receives `ctx.sessionID` and calls galopin's own loopback endpoint, bearer-authenticated with a per-process random token that only opencode's environment holds. A local MCP server is **not** a route: verified against 1.18.32, an MCP `tools/call` carries only `{name, arguments, _meta.progressToken}` and nothing that names the calling session.)

**Galopin owns the approval.** opencode runs a custom tool without asking anything, so `session_spawn` and `session_send` do not depend on opencode's permission system at all: the tool call blocks inside galopin's loopback handler, galopin emits its own `permission.asked` for it (below), and, unless it is auto-approved ("Auto-approval" below), the call proceeds only when a person answers `permission.reply` with `once` (`always` is treated as `once` — nothing is ever remembered). The request `id` is minted by galopin and has the prefix `gp_`; a `permission.reply` on such an id resolves galopin's held call and never reaches opencode. Once raised it is **never auto-accepted, whatever the flags** — the session's flag, an ancestor's inherited flag, `Policy.autoAccept` — by a check on the request itself (`metadata.galopin == true`), not on the tool's name: `isHandoffApproval`'s substring rule is neither relied on nor extended (verified: it does not match `session_spawn`, and an auto-accepting session would have approved it). `reject`, or the session's turn being cancelled while the ask is pending, makes the tool return a refusal text to the model; a cancelled turn also closes the held ask with `permission.replied {decision:"reject", by:"user"}`. `session_list` only reads, needs no approval and is audited.

**Auto-approval (decided before the ask).** Galopin decides BEFORE it raises the ask, and when it decides yes no `gp_` ask exists at all — nothing is auto-_replied_, so the never-auto-accepted rule above is untouched. A `session_spawn` or `session_send` is approved without a card only when **the caller's auto-accept is in effect** (the session's flag or an ancestor's, AND `Policy.autoAccept` allowing it — the machine's veto still vetoes) and, **for a send only, the target is in the sender's own workspace** (the sender's unattended power covers its own workspace only, so a cross-workspace send always shows the card) **and its mode is equal to or stricter than the sender's** by the same `modeRank`. **Anything unknown on either side asks**: a mode outside the table (a custom one) or an empty mode (the backend's default agent, which galopin has not verified, so a session with no explicit mode is never ranked) — the sender's included, since a custom sender may be more restricted than `build`. So two custom-mode sessions never auto-send to each other, and neither do sessions created without a mode. A spawn needs no target check: the child is equal-or-stricter by construction (a caller with no explicit mode may only request `plan` or inherit, for the same reason), starts with auto-accept off and asks for its own tools. A send borrows the target's powers, which is why only it carries the target condition. Everything else is asked exactly as before: a plan sender to a build target, a send to another workspace, any send to a more permissive or unrankable target or from an unrankable sender, and every send while the machine denies auto-accept. **Handoffs and questions are never auto-approved.** `enroll --no-agent-tools` (and `galopin policy set --no-agent-tools`) still turns the tools off entirely.

_Hop and rate._ A send at hop 4 or more is **not refused**: it falls back to the approval card (`hop` in its metadata keeps counting; auto-approval applies only within hops 1–3), which is what lets two sessions carry on a long exchange with a person clearing it every step. The per-pair rate limit is unchanged and stays a **hard refusal** — it is the loop brake, under auto-accept or not.

_Visibility._ An auto-approved call is audited as `agent_tool {tool, from, decision:"auto", reason}` (reason `"auto-accept; target no more permissive"` for a send, `"auto-accept; spawned session is no more permissive and starts with auto-accept off"` for a spawn; a spawn's `to` is on the `done` row that follows) and the tool result carries `"autoApproved": true` (a spawn's `{"sessionId","title","mode","autoApproved":true}`; a send's `{"autoApproved":true}` in place of `{}`), which Cerea renders as an **auto-approved** badge on the sender's "Spawned …" / "Sent to …" card. The approval card itself is unchanged when it is shown.

_The residual, stated plainly._ An auto-accepting session can now message equal-or-stricter peers without anyone seeing a card. That is power it already holds unattended — it can already run its own tools without asking — so this adds no new capability. What it adds is exposure: noise, and a peer session's context being steered by another agent's text. That exposure is bounded by the hop and rate limits (a chain past 3 hops needs a person; five sends a minute per pair), and it is never invisible: every one is an audit row and a badge.

The approval card is the existing `PermissionRequest`, filled in like this:

```
session_spawn: {id:"gp_…", sessionId, tool:"session_spawn", title:"Start a new session: <title>", callId, messageId,
                patterns:[], always:[],
                metadata:{galopin:true, title, modeId, modelId|null, workspaceId, prompt}}
session_send:  {id:"gp_…", sessionId, tool:"session_send", title:"Send a message to <target title>", callId, messageId,
                patterns:[], always:[],
                metadata:{galopin:true, target:{sessionId, title, workspaceId}, text, hop}}
```

`prompt` and `text` are shown in full, up to 8 KiB; a longer one is refused before any ask is raised, so a card never shows a truncation the model did not make. `modeId` is the mode the child will actually get. Every tool call, allowed or refused, is a row in `audit.log`: `agent_tool {tool, from, to?, decision:"done"|"refused"|"auto", reason?}` — one row naming both sessions (`from` the caller, `to` the spawned child or the addressed session), never the prompt or text.

**The caller is verified.** The relay token proves only that opencode made the call, so galopin also requires the event stream to show an unfinished tool part with the relayed `callId` and tool name in the named session (waiting up to 5 s for it to arrive): a session id alone, written by anything holding the token, borrows no other session's mode, workspace or standing. A call it cannot match is refused.

**`session_list {note}`** (`note` is ignored; opencode requires an argument) → the machine's non-archived **top-level** sessions, `[{sessionId, title, workspaceId, workspace, mode, status, spawnedBy?, note?}]` (`mode` is `"default"` when none is set; `note` marks the caller's own tree, not a send target). Subagents, archived and untracked sessions are absent; the listing refreshes galopin's tracking first, so a restarted galopin still addresses every session.

**`session_spawn {title, prompt, mode}`** (`mode` is `"plan"`, `"build"` or `"inherit"`; opencode marks every argument of a dependency-free tool required, so "leave it out" is spelled `"inherit"`) → `{sessionId}` once the person approved and the child's first prompt was accepted (the child's turn then runs on its own). The gates, in order, each refusal a tool error the model reads:

1. the workspace is **always the caller's own** — there is no argument for another, and a `workspaceId`- or `directory`-shaped argument is refused, not ignored;
2. `mode` defaults to the caller's; a given one must be **equal or more restrictive** (galopin's own order: `plan` is more restrictive than `build`; a mode outside that table can only be the caller's own) — never an escalation;
3. the model is the caller's, under the `allowFreeModels` gate exactly as `session.setModel`;
4. the child's auto-accept is **off**, whatever the caller or an ancestor has; the child is a new **top-level** session (`parentId: null`), not a subagent, so nothing is inherited;
5. fork-bomb limits: a spawn chain at most 2 deep (`spawnedBy` links; a session at depth 2 cannot spawn), at most 3 live (not archived, not finished) spawned sessions per root, at most 6 spawn attempts per root per 10 minutes — all refused before an ask is raised, so a looping model cannot flood the card list;
6. then the approval; then the child is created with its `spawnedBy` marker (§7) and prompted.

**`session_send {target, text}`** → `{}` (`{"autoApproved":true}` when auto-approved) once the person approved (or it was auto-approved) and the target accepted the prompt. `target` is a `sessionId` from `session_list`. The gates, in order: same machine only (an id galopin does not list is refused); the target is a non-archived **top-level** session; **no self and no same-tree sends** (the target's root is the caller's root: yourself, your subagents, your ancestors, your siblings — use `task` for those); `hop` — the sender's current hop (the `sentBy.hop` of the message that started its running turn, else `0`) plus 1 — above 3 the send is asked (never auto-approved, never refused for hop alone); at most 5 sends per minute per ordered sender→target pair (a hard refusal); then the approval, or its auto-approval (above); then delivery as an ordinary prompt (opencode `prompt_async`), so a **busy target folds it into its running turn** (capability `steer`) instead of queueing behind it. The message the target sees carries `sentBy` (§7), and its text names the sender, so the target's model never mistakes it for its person.

**Result shapes (pinned).** A tool part's `output` on success: `session_spawn` → a JSON object `{"sessionId", "title", "mode"}` (`sessionId` is the contract, the rest informative; plus `"autoApproved": true` when auto-approved); `session_send` → exactly `{}`, or `{"autoApproved":true}` when auto-approved; `session_list` → the JSON array above. Every refusal — any gate above, a declined approval, an internal failure, an aborted call — makes the tool part `status:"error"` and its `error` text **exactly a JSON object `{"refused": "<reason>"}`** (`reason` is plain prose for the model and the person; never parse it further). A cancelled turn's held call ends the same way. So a client reads one shape: `status:"completed"` → success shape above, `status:"error"` → `JSON.parse(error).refused`.

Refusals never touch the wire beyond that: no new error codes and no new ops. A machine without `agentTools` simply has no such tools.

**Background subagents (opencode 1.18.32, `Policy.backgroundSubagents`).** opencode's own `task` tool — not galopin's `session_*` tools above — gains `background:true` behind `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`, which galopin sets only when the machine enrolled with `--allow-background-subagents` (denied strips any inherited value, so `background:true` fails closed with "Background subagents require OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true"). No new spawn path and no `session_spawn` change: with `background:true` the child keeps running after its parent turn ends and opencode injects the result back as a synthetic text part `<task id state><summary>…</summary><task_result|task_error>…</…></task>` on the parent; `task_id` follows up that same running child (a follow-up, never a new spawn); `POST /experimental/session/:id/background` ("Background subagents") detaches a blocking synchronous child into the same state. Children stay in the same exposed tree (`session.children`, `parentId`, `rootSessionId` fan-out) — the only new shapes are the task tool's `output` carrying `<task … state="running">` and the synthetic completion part, which Cerea folds into one visible parent marker per child (running, then completed or failed) rather than model text. The marker says only what opencode reported: a `task_id` resume reads as a follow-up, and the injected result reads as automatic.

## 7. Events (the normalized stream)

Envelope: `{sessionId, epoch, seq, rootSessionId, event}`. `epoch` is a random id minted when the agent process starts (its in-memory buffers are lost on restart, so a new epoch means "resync from snapshot"). `seq` is per session, starts at 1 in each epoch, strictly increasing, no gaps. `rootSessionId` is the top-level ancestor of `sessionId` (itself for a top-level session); the materializer learns the parent edge from `Session.parentId` (tracked sessions, `session` events, `session.children`) and from the parent's own task/subtask parts naming the child they spawned. Identity-based dedup is on `(epoch, seq)` only, never on content (R3/R4).

**Subagent auto-accept inheritance.** Auto-accept is still a per-session flag, but a `permission.asked` for a session without its own flag walks up to the root: it auto-replies when any ancestor has auto-accept on and the machine policy allows it (`Policy.autoAccept`). Handoff approvals (a permission whose tool is a handoff) are never auto-accepted, whatever the flags say. Questions are never auto-accepted either — auto-accept's scope is tool-call permissions only. Neither are galopin's own approvals (`metadata.galopin`, §6 Agent tools), which are recognised by the request itself, not by the tool's name — galopin instead decides whether to raise one at all (§6 "Auto-approval").

`Part = {id, messageId, role, type, …}` by `type`:

- `text` `{text, synthetic?: bool}` (synthetic parts are backend-injected; Cerea does not show them as user text — except a background task's `<task>` result injection, which folds into that child's parent marker as completed or failed, labelled automatic)
- `reasoning` `{text}`
- `tool` `{callId, tool, status:"pending"|"running"|"completed"|"error", title?, input{}, output?, error?, attachments?: ToolAttachment[]}` — `attachments` (capability `toolImages`) lists the images the call produced, by reference and never with bytes: `ToolAttachment = {sha256, mime, size, filename?}`, `sha256` the lowercase hex digest of the _decoded_ image computed on the machine, `mime` one of `image/png|jpeg|gif|webp`, `size` the decoded byte count, at most 8 per call, each at most 8 MiB; the part's `attachmentsOmitted` (int, omitted when 0) counts the images it produced that are not listed (over the cap or size, or not a raster type), so a card can say so. Nothing else is listed — SVG, non-`data:` URLs and non-image parts are dropped machine-side. The list rides the part like any field, so a snapshot (`session.sync`, a reload) and the live `part` event carry the same one; bytes come from `session.attachment` (§6) only. **opencode:** (galopin reads the event stream with a bounded line reader — 128 MiB — because a tool part carries its images inline in one line; a longer line is skipped without dropping the stream and its session is resynced from the transcript, tool parts re-announced) the completed tool state's `attachments` (image `FilePart`s whose `url` is a `data:` URL — where a browser tool's screenshot lands; verified live against 1.18.32, where the built-in `read` tool on an image file produces one too, re-encoded by opencode itself when large). **ACP:** `tool_call`/`tool_call_update` content items `{type:"content", content:{type:"image", data, mimeType}}` (verified live against `opencode acp`); a later update that repeats the call without content keeps the images.
- `file` `{mime, filename?, url?}`
- `subtask` `{sessionId?, description?, agent?}` (a subagent spawn)
- `compaction` `{auto: bool}` — a marker part on the assistant message that summarized the session (opencode: `CompactionPart`, verified against 1.18.31's `GET /doc`; carried as an ordinary part on `message.part.updated`/the transcript, not a separate event kind). `auto` distinguishes opencode's own context-overflow trigger from a person's "Compact now". opencode's OpenAPI also has richer `session.next.compaction.{started,delta,ended}`/`session.compacted` broadcast events (progress text, `reason: auto|manual`) that this backend does not map — the `compaction` part is the single signal Cerea needs, per §8.

The agent is subscribed to its backend from process start, so it has seen every event of every session touched since; for sessions untouched since start, the backend's persisted transcript is exact. The snapshot therefore equals "persisted transcript + everything applied since", with no gap.

**Questions and the generic tool part.** A question call also rides an ordinary `tool` part (`tool:"question"`, `status: pending→running→completed|error`, `input` carrying the same `questions` array) — the same double-reporting `permission.asked` already has alongside a tool part, and for the same reason: the transcript's own tool-call rendering keeps working even for a client that does not special-case questions, while `question.asked`/`question.resolved` are what the approval card actually answers through.

**Usage on `Session` (`session.get`/`session.list`).** opencode's own session object carries no usage field — only assistant messages do — so the agent caches each session's latest `Usage` as it is observed on the event stream (or when `Transcript` is fetched) and answers `session.get`/`session.list` from that cache. A session this process has not touched since it started (no event, no `Transcript` call) answers with `usage: null`; the caller's `session.sync` snapshot (which does read the persisted transcript) is what backfills that case, per the no-gap guarantee above.

## 8. Cerea side (what maps to what)

- The browser-facing API is `/api/v2/code/v1/...?device=` plus `/api/v2/code/agents/[id]/stream`. Behind it, the forwarder (`src/routes/api/v2/code/[...path]/+server.ts`) maps each allowed path to one typed op on the device's `MachineLink` (`src/lib/server/code/machines.ts`), sent over the machine's socket.
- SSE bridge: register a fan-out listener (buffering), `session.sync` with the browser's `Last-Event-ID` (`<epoch>:<seq>`), emit (snapshot → chat frames, or the missing events), then drain buffered live events with `seq >` the sync's `seq`. SSE `id` = `<epoch>:<seq>` of the last envelope a frame came from. Epoch change → a `reset` event that makes the client re-fold from scratch. No per-frame info logs (R6).
- Mapping normalized → chat `AgentStreamUpdate` (`src/lib/server/code/machineTimeline.ts`): user `text` part (non-synthetic) → `user`; assistant `text` part/delta → `Stream`; `tool` part → Tool call / result / error (uuid = callId); `permission.asked/replied` → Elicitation request/resolved; `question.asked/resolved` → the same Elicitation request/resolved (the user-question tool design: normalized questions become `ElicitationField[]`, the same shape and card — `AskQuestion.svelte` — chat's own `ask_user_question` already uses); `status busy` → TurnState running, `idle` → done (failed if the last assistant message carries `error`); `error` → TurnState failed; `todo` → Plan; `usage` → a side-channel frame (M3).

**Tool-output images.** A completed `tool` part's `attachments` map, in the same function for a snapshot and a live event, to a second entry in the result frame's `outputs`: `{content: [{type:"image", mimeType, url}]}`, where `url` is `<base>/api/v2/code/v1/agents/<sessionId>/attachments/<sha256>?device=<id>` — the forwarder's raw route below — beside the `data:` images an MCP tool's result already carried (`ToolUpdate.svelte` renders both; a `url` is loaded only if it is a same-origin path). Cerea keeps only well-formed entries (64-hex sha, raster mime, 0 < size ≤ 8 MiB) and at most 8 per call, and appends a text output ("N images not shown …") for `attachmentsOmitted` plus any entry it dropped. `ToolUpdate.svelte` loads a `url` only if it is exactly this route's URL (`…/agents/<id>/attachments/<64 hex>?device=<24 hex>`), never any other path. Bytes never ride the stream, and **nothing is persisted in Cerea**: no image, no url, no capability at rest — the machine is asked again on every view and the browser caches the answer.

`GET /api/v2/code/v1/agents/:id/attachments/:sha256?device=` (the forwarder's raw route; `:sha256` must be 64 lowercase hex) calls `session.attachment`. It has the forwarder's usual authorization (§4: the signed-in person, their paired device, the machine's live link); the sha in the URL is **not** a capability — the op answers only for that session's own images. Because the machine is untrusted (a compromised one is assumed possible), Cerea judges the _bytes_, not the machine's word:

- the type comes from the **magic numbers** against the raster allowlist (PNG, JPEG, GIF, WebP) and the claimed `mime` is ignored — a PNG labelled `text/html` is served as `image/png`, SVG/HTML/text labelled `image/png` is `415`;
- width × height is read from the header (PNG IHDR, the JPEG frame header, GIF, all three WebP variants); more than **50 megapixels**, zero, or a header that cannot be read is `413` — a decompression bomb is a few dozen bytes;
- more than **8 MiB** is `413`, checked on the base64 length before decoding;
- the bytes must hash to the requested sha, else `502` (this is what makes the caching below sound);
- the response is `Content-Type` from the bytes, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cache-Control: private, max-age=31536000, immutable` (keyed by sha; private because a shared cache must not keep a person's screenshots);
- machine answers map as elsewhere: `not_found` (unknown, or "no longer on the machine") and `unsupported` are `404`; a view is audited (`attachment.raw`, session/sha and byte count, never content).

Known limit: a broken image is what a person sees for an image the machine no longer has (ACP after a galopin restart, or an opencode session whose history was compacted away); the 404 body names why.

## 9. Machine powers: files and terminals (specified by ADR 0090; F1 and T1 build it)

**Implemented so far (F1a):** `files.list`, `files.stat`, `files.read` and `files.status`; the `files` and `fileDeny` policy fields with `enroll --no-files`, `--file-deny GLOB` and `--no-default-file-deny`; `hello.machine.capabilities.files: true` (the rest false). The error codes `conflict` and `too_large` are in both halves.

Additive only: `protocol` stays `1`. Everything here exists only when `hello.machine.capabilities` says so, and an unknown op still answers `unsupported`, so an old Cerea paired with a new galopin works unchanged, and so does the reverse. These are **machine ops**: galopin dispatches `files.*` and `terminal.*` before the backend switch, and they never call opencode or an ACP agent. opencode's own `/file*`, `/find*` and `/pty` are deliberately not used.

A power is live only when the machine policy (§4), the deployment switch (`CODE_FILES_ENABLED`, `CODE_FILE_WRITE_ENABLED`, `CODE_TERMINAL_ENABLED`) and the capability all allow it. Cerea checks the first two before forwarding, answering 403 with the exact enroll flag, and galopin enforces the policy again.

### 9.1 Paths and confinement

- Paths are **workspace-relative**, `/`-separated, with no leading `/` and no `..` segments (`invalid` otherwise). `"."` is the root.
- Every access goes through Go's `os.Root` for the workspace (openat-based, so no TOCTOU). A symlink whose target escapes the root is listed with `escapes: true` and never followed or read.
- `.git/` is skipped. Dotfiles are listed with `hidden: true`. `fileDeny` matches are redacted.

### 9.2 Binary frames (terminal streams only)

galopin sends these only on a channel Cerea opened with `terminal.attach`, so a peer that does not know them never receives one.

```
byte 0        kind   0x01 term.output (M→C) · 0x02 term.input (C→M) · 0x03 term.ack (C→M)
byte 1        L      channel id length, 1..32
bytes 2..L+1  channel id, ASCII [A-Za-z0-9_-] (chosen by Cerea in terminal.attach, one per viewer)
next 8 bytes  u64 big-endian offset
                term.output: absolute output offset of the payload's first byte
                term.ack:    the viewer has consumed output up to (excluding) this offset
                term.input:  0
rest          payload: raw bytes. term.output ≤ 32 KiB; term.input ≤ 16 KiB; term.ack empty
```

Unknown kinds are ignored. Offsets are per terminal, start at 0 when it is spawned, and never reset for its life. Terminals die with the galopin process.

**Flow control:**

- galopin's writer has two lanes. Control (`res`, `event`, `notice`, `credential`, `auth`) is always drained before stream frames, which are at most 32 KiB each.
- Per channel, galopin sends output only while `sent − acked ≤ 256 KiB`. Acks come from the browser, after xterm has processed each 64 KiB, and Cerea relays them.
- Out of credit, galopin stops reading that PTY. With no viewer attached, or every viewer out of credit for 10 s, it keeps reading into its 2 MiB ring and drops the oldest bytes.
- A viewer that comes back behind the ring start gets `reset`.

**Terminal process rules:**

- It runs `$SHELL -l` (falling back to `/bin/sh`) in a `cwd` inside the workspace root, with `TERM=xterm-256color`.
- Its environment is **scrubbed** of everything galopin injected for itself: the opencode server password, the shim secret, and any token or refresh variable.
- Exited terminals are kept 10 minutes for display (not counted against `maxTerminals`), unless `terminal.close` drops one sooner. A terminal with no viewer for 24 h gets SIGHUP.
- All terminals are closed on `run` shutdown and on a 4403 revoke.

### 9.4 Default `fileDeny`

`.env` · `.env.*` except `.env.example`, `.env.sample` and `.env.template` · `.envrc` · `*.pem` · `*.key` · `*.p12` · `*.pfx` · `*.kdbx` · `id_rsa*`, `id_ecdsa*`, `id_ed25519*` · `.netrc` · `.npmrc` · `.pypirc` · `.git-credentials` · `.aws/credentials` · `.docker/config.json` · `*.tfstate` · `secrets.y*ml`.

The deny list prevents **accidental** exposure: screen sharing, and content flowing through Cerea into logs or caches. It is **not** a security boundary once a terminal or the agent can read the file, and the UI says so.

### 9.5 Notices

`{"type":"notice","scope":{"workspaceId"?:"…","terminalId"?:"…"},"event":Notice}` frames are machine-level and lossy: no epoch or seq, no replay. A receiver that might have missed some re-queries `files.status` or `terminal.list`. `files.changed` is debounced to 200 ms with at most 256 paths; beyond that it carries `overflow: true`, and the receiver refreshes everything.

### 9.6 Browser side (Cerea)

- **Files:** REST on the forwarder, with the same `getPairedDevice` check. `conflict` maps to 409, `too_large` to 413, and `unsupported` to 404. The raw route serves only raster images inline, with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`. Anything else goes as `text/plain` or an attachment, never as HTML or SVG.
- **Terminal:** a browser WebSocket.
  1. `POST …/terminals/:id/ticket` passes through the hooks and returns a single-use ticket: 256 bits, 30 s, bound to user, session, device and terminal.
  2. Minting requires an OIDC `auth_time` within 12 h (otherwise re-login), plus the one-time acknowledgement per machine.
  3. The upgrade at `${base}/api/v2/code/terminal?ticket=…` redeems the ticket and requires `Origin` to equal the public origin.
  4. The socket re-checks the session and the device every 60 s and closes with 4403 on logout, revoke or unpair.
- **Audit:** Cerea `codeAudit` (90-day TTL) and galopin's local `audit.log` record actions (terminal open, attach and close; file writes; refusals; ticket failures). They never record keystrokes, output or file content.
