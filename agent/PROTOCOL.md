# Thin machine agent: architecture and wire protocol (v1)

Status: implemented (P0 and parity milestones 1–9, 2026-09-24; live since the deploy-rearch cutover). This is the `/code` data path (ADR 0089, which supersedes 0085).
Source of truth for both implementations: the Go agent, galopin (this repository's `agent/`, moved from Pystino `deploy/agent/` with its history preserved), and Cerea's machine link (`src/lib/server/code/machine*.ts`).

The move and rename left this protocol itself untouched on purpose — live
machines depend on it: the subprotocol (`pystino-machine.v1`, §3), the WSS
path (`/api/v2/code/machine`), the `X-Pystino-Machine-*` headers (§3) and
the `opencode-enrollment` OIDC client id all keep their names below. Only
the binary, its log prefixes, its on-disk state directory and its packaging
are galopin now; nothing on the wire changed.

## 1. Shape

```
 browser ──HTTPS (existing /api/v2/code/* REST + SSE)──► Cerea server
                                                          ▲
                                   WSS, dialled OUT by the machine, bearer = enrollment access token
                                                          │
 user's machine:  galopin run
                   ├─ link      : WSS client to Cerea, reconnect w/ backoff, token renewal frames
                   ├─ sessions  : backend-agnostic materializer (epoch/seq, ring buffer, policy)
                   ├─ backend   : Backend interface; first impl = opencode (supervises `opencode serve`)
                   └─ shim      : the existing /v1 proxy (injects the gateway bearer + x-bill-to), now with a local secret + Host allowlist
                                   opencode ──HTTP──► shim ──HTTPS──► Pystino /v1
```

- **One binary** (`galopin`, grown from `pystino-enroll` by way of `pystino-agent`), no Node/npm/Python on the machine besides opencode itself.
- **One credential root**: the enrollment's OIDC refresh token. The same access token authenticates the WSS to Cerea and the `/v1` calls. Revoking at the IdP kills both within one access-token lifetime.
- **Nothing capability-bearing is stored in Cerea.** Cerea holds only a live socket that the machine opened. A DB dump yields device names and ids, nothing that can reach a machine.
- LLM traffic never crosses Cerea (unchanged two-path rule).

## 2. Why this backend interface, and not ACP as the interface

We checked `opencode serve` (1.18.31, OpenAPI at `GET /doc`) against ACP (Agent Client Protocol).

- `opencode serve` gives, over HTTP + one SSE stream (`GET /global/event`, all directories): sessions (`POST/GET/PATCH/DELETE /session`), async prompt (`POST /session/:id/prompt_async`, `parts[]` with text and file parts, per-prompt `agent` = mode and `model`), abort, permissions (`permission.asked` event, `POST /permission/:id/reply {reply: once|always|reject}`), questions, modes (`GET /agent`, `mode: primary`), models (`GET /config/providers`), per-session diffs (`GET /session/:id/diff`, `session.diff` event), children (subagents, `GET /session/:id/children`), todos, usage (tokens and cost on assistant messages / step-finish parts), compaction (`POST /session/:id/summarize`, a required `{providerID, modelID, auto}` body — the model: the session overlay's, else the newest assistant message's, else `GET /config`'s `model`; an empty body is a 400), revert, worktrees (`/experimental/worktree`), basic auth (`OPENCODE_SERVER_PASSWORD`). Sessions persist across restarts.
- ACP (JSON-RPC over stdio) covers the core: `session/new|load|prompt|cancel|set_mode|set_model`, `session/update` notifications (message/thought chunks, tool_call(+update), plan, mode updates), `session/request_permission` with allow/reject once/always options, image/resource content blocks. It lacks (or has only unstable drafts for) session listing, usage/context, diffs, subagent trees and multi-client attach; the client owns the process.

**Decision:** our own backend interface, _shaped like ACP_ (same nouns: session, prompt, update stream, permission request with once/always/reject, cancel, mode, model) plus optional capabilities for what ACP lacks (usage, diff, children, compact, worktrees). opencode is implemented over `opencode serve` (richer than `opencode acp`, survives restarts, multi-directory). The generic **ACP adapter** is the natural _second_ backend (covers Gemini CLI, Claude Code and Codex via their ACP adapters, Pi via `pi-acp`); it simply reports fewer capabilities. Capabilities are advertised per backend in `hello`, and Cerea hides affordances a backend lacks.

`galopin run --backend acp --acp-command "<cmd…>"` (default `opencode acp`) runs the generic adapter (`internal/backend/acp`) instead of the default `opencode` backend; `--backend opencode` (or omitting the flag) keeps the default. The adapter spawns and supervises `<cmd…>` (restart with backoff, process group + `Pdeathsig`, same discipline as opencode's own supervisor) and speaks JSON-RPC 2.0 newline-delimited over its stdio. `initialize` (no fs/terminal client capabilities) seeds `ID()`/`Version()` (`acp:<agentInfo.name>`) and `Capabilities()` (Images from `promptCapabilities.image`; Diff/Children/Usage/Compact/Worktrees always false, since ACP has no wire message for any of them; No `autoAccept` capability any more (auto-accept is gone), and no selector: an ACP agent has no permission rules galopin can read or compose, so its `session/request_permission` asks reach a person as they come). Prompts map to `session/prompt`'s content blocks and return once sent (the async contract); the turn's completion arrives later as a `status` event once the response carries `stopReason` (`cancelled` → idle; `refusal`/an RPC error → `error`). `session/update` notifications become the normalized event stream, with ids derived from a local turn counter rather than the agent's own per-chunk ids, so "one message per turn per role" holds regardless of how a given agent chunks its output. `session/request_permission` becomes `permission.asked`; `ReplyPermission` answers with the `optionId` of kind `allow_once`/`allow_always`/`reject_once` (with fallbacks); a `Cancel` with a permission pending answers it `{outcome:{outcome:"cancelled"}}` first. `session.rename`/`session.delete` are best effort (a title overlay; `session/close` if advertised); `session.setModel` (the still-unstable `session/set_model`) reports the agent's error cleanly if unsupported. Verified live against opencode 1.18.31's `opencode acp` (see `acp_it_test.go`), including the one spot it diverges from the published ACP schema: `session/new` answers with a bespoke `configOptions` list rather than `modes`/`models` — both shapes are read.

## 3. Transport and authentication

- Endpoint: `GET wss://<cerea-origin>/api/v2/code/machine` (WebSocket upgrade), subprotocol `pystino-machine.v1`.
- Headers: `Authorization: Bearer <access token>`, `X-Pystino-Machine-Id: <uuid>` (generated once, persisted in the agent state dir; a re-enroll mints a new one), `X-Pystino-Machine-Name: <display name>`.
- Cerea validates the JWT **locally** (JWKS from the issuer's discovery doc, cached): `iss` == configured issuer (`OPENID_PROVIDER_URL`, exact, trailing-slash-normalized); `aud` contains `CODE_MACHINE_AUDIENCE` (default `pystino-api`); `azp` (or `client_id`) == `CODE_MACHINE_CLIENT_ID` (default `opencode-enrollment`); `exp` in the future; `typ` header, if present, is not an ID token. Userinfo is never used. This is review C1 done properly for the one thing a machine presents.
- The token's `sub` must map to an existing Cerea user (same mapping the OIDC login uses). No user → close `4403 "sign in to Cerea once before connecting a machine"`.
- Handshake rejections happen **before** the upgrade completes when possible (HTTP 401/403), otherwise as close codes:
  `4401` token invalid/expired · `4403` forbidden (revoked device, unknown user) · `4409` a newer connection for the same machine replaced this one · `4000` protocol error.
- **Token renewal:** the agent refreshes its access token at ~70% of lifetime and sends `{"type":"auth","token":"…"}`. Cerea re-validates (same `sub`, same checks) and moves the connection's deadline. Cerea closes with `4401` when `exp + 60s` passes without renewal. That makes IdP-side revocation effective within one access-token lifetime.
- Keepalive: WebSocket ping every 20 s from Cerea; the agent treats 60 s of silence as dead and reconnects. Agent reconnect: exponential backoff 1 s → 30 s with jitter, never gives up except on `4403`.
- **Deadlines everywhere (R1):** the dial has a 10 s timeout; every Cerea→machine request has a deadline (default 15 s, `session.sync` 20 s). An offline machine answers "offline" instantly from the registry, never hangs.

## 4. Pairing and authorization (per user, per device, revocable)

- A machine connecting with a valid token and an unknown `machineId` creates a `codeDevices` row `{userId, machineId, name, status: "pending", sub, iss, createdAt}` (unique index `(userId, machineId)`). The socket stays open but **no operations are forwarded** until the owner confirms.
- The `/code` panel lists pending machines with **Confirm / Reject**. Confirm → `status: "paired"` and Cerea sends `{"type":"status","status":"paired"}` down the socket. This click is the fresh human approval review C2 asks for; a phished device-code approval alone never reaches the panel's operations.
- Revoke (DELETE device) → row becomes `status: "revoked"` (tombstone keyed by machineId), the live socket is closed with `4403`, and further connects with that machineId are refused. Re-enrolling mints a new machineId → a new pending row.
- Every browser request is authorized as: `locals.user` present (C6) → device row with `userId == locals.user._id` and `status == "paired"` → the live connection for that row is authenticated as the same `sub`. A device can never be driven by a user other than the one whose credential the machine holds (C10 closed by construction; there is no paste flow).
- **Machine-side policy (the machine's veto, C4):** `galopin` has a local policy file (`policy.json` in its config dir, set by `enroll` flags, never writable over the link):
  - `permission` (§6 "Permissions"): `{rules, max}`, none of it writable over the link.
    - `max` — the **ceiling**: permission key → `"ask" | "deny"` (a key absent is uncapped). The most that key may ever be, whatever any rule, any session's selector, any "always allow" or any reply says. `enroll --permission-max KEY=ACTION` (repeatable; the default is `bash=ask` alone, see the residual in §6 "Permissions"; a list given replaces the default; `session_read` and `session_send` are ceiling keys like any other and uncapped by default); `galopin policy set --permission-max` may only lower it, and a running agent takes the lowering in within seconds.
    - `rules` — the machine's **own rules**: key → `"allow" | "ask" | "deny"`, applied to every session as session rules, so they beat the static `opencode.json` that `enroll` wrote, and the ceiling caps them. `enroll --permission-rule KEY=ACTION`; `policy set` may only lower or add an ask/deny.
    - There is no `responders` any more: auto-accept (a client-side responder answering asks `once`) was replaced by the per-session Deny / Ask / Allow selector (§6 "Permissions"), which a person sets and which is never a machine setting. An older `policy.json` may still carry `permission.responders` or the legacy `autoAccept`; both are ignored on read and dropped on the next save. `enroll --allow-auto-accept` and `policy set --no-auto-accept` are accepted for one more release as no-ops that print a warning, then deleted. The machine's **ceiling** (`max`) is the only thing a session's selector can never go past.
  - `workspaceRoots`: absolute paths; if non-empty, `workspace.create` outside them is refused.
  - `allowFreeModels`: bool (default false). When false the agent lists and accepts only gateway (`pystino/*`) models; Cerea filters as well (defence in depth).
  - Machine powers (ADR 0090, §9; partly built, see the status line at the top of §9; each exists only when `hello.machine.capabilities` says so):
    - `files`: `"read" | "off"` (default `"read"`; `enroll --no-files`). `off` answers every `files.*` op `forbidden`.
    - `fileWrite`: `"allowed" | "denied"` (default `denied`; `enroll --allow-file-write`). Gates `files.write`. **Specified, not built:** no such policy field or flag exists yet.
    - `fileDeny`: glob list (default: the §9.4 list; `enroll --file-deny GLOB` adds, `--no-default-file-deny` drops the defaults). Matching entries are listed with `redacted: true`, reading them is `forbidden`, and search skips them.
    - `terminal`: `"allowed" | "denied"` (`enroll` writes `allowed` unless `--no-terminal`; a file without the field, from an older enroll, reads `denied`). Gates every `terminal.*` op.
    - `maxTerminals`: int (default 8). `terminal.open` beyond it is `invalid`; a terminal kept around only for exit-retention display does not count against it.
    - `commandShell`: `"allowed" | "denied"` (`enroll` writes `allowed` unless `--no-command-shell`; a file without the field reads `denied`). Gates `session.command` (§6): while denied, a command whose template expands `` !`…` `` shell — and every command whose shell fact is _unknown_ (an MCP prompt, an ACP command), because nobody has seen a template to scan — is refused `forbidden`. The expansion runs inside opencode before any permission rule is asked, so it is off until an owner explicitly opts in.
    - `agentTools`: `"allowed" | "denied"` (default `allowed`; `enroll --no-agent-tools`, and `galopin policy set --no-agent-tools` to tighten later). The one power that is on by default: `session_read`/`session_spawn`/`session_send` add nothing without a per-call approval unless the machine's own rule for that tool says allow, or the session was granted it with `session.grantCoordination` (§6 "Permissions") — or, for a session on Allow, the blanket over the two mutating session tools (below). A spawned session inherits its spawner's permission word, coordination grant and exceptions, never more (it starts on Ask exactly when its spawner is on Ask). `denied` installs **no** galopin tool into the backend (`OPENCODE_CONFIG_DIR` is not set by galopin) and the backend reports `agentTools:false`; `steer` is unaffected (it is about a person's own mid-turn prompts and is reported from the backend alone). Takes effect at the next `run`. Older machines omit the field.
    - `projectConfig`: `"allowed" | "denied"` (default `denied`; `enroll --allow-project-config` opens it, `galopin policy set --no-project-config` tightens later). Denied starts `opencode serve` with `OPENCODE_DISABLE_PROJECT_CONFIG=1 --pure`: a workspace's `opencode.json`, `.opencode/` commands/agents/MCP and `AGENTS.md`/`CLAUDE.md` are not loaded (known gap, 1.18.32: a repo's `.opencode/plugin(s)` scripts still run). Allowed loads them and pins the gateway config over the repo's as `OPENCODE_CONFIG_CONTENT` (provider, `enabled_providers`, `model`, `small_model`); a repo setting any routing key is audited as `project_config.override_attempt {keys}`. `workspace.list` entries carry `projectConfigIgnored: true` when the machine denies and the repo carries such config. Older machines omit the field and load project config.
    - `backgroundSubagents`: `"allowed" | "denied"` (`enroll` writes `allowed` unless `--no-background-subagents`; a file without the field reads `denied`; `galopin policy set --no-background-subagents` tightens later). Allowed starts `opencode serve` with `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=1`, so the task tool accepts `background:true`: the child keeps running after its parent turn ends and its result is injected back as a synthetic `<task>` message the panel folds into a visible parent marker. Denied never sets the flag (any inherited value is stripped), so `background:true` fails closed inside opencode. Takes effect at the next `run`. Older machines omit the field, read as denied.
    - A local `galopin policy set` may only tighten these; loosening needs `enroll`.
  - The policy is reported in `hello` so the UI can explain refusals.

What this achieves: no capability at rest in Cerea; per-device, per-user authority that ends on revoke (socket closed, machineId tombstoned) or on IdP revocation (≤ one token lifetime); the machine's ceiling caps every session's selector, and it can confine workspaces. What it does **not** achieve: while a machine is connected and paired, a compromised Cerea process can still send prompts to it within the machine's policy (the panel is, by design, a remote control). Mitigations beyond that (per-prompt signing by the browser) are out of scope for v1.

JSON text frames, one object per frame, `type` discriminates.

| C→M               | `{"type":"welcome","deviceId":"<ObjectId hex>","status":"pending"\|"paired","features":{"machineCalls":["schedule"]}}` — `features` is optional; `machineCalls` lists the call families (below) this Cerea answers                                                                                                                                                                                                                                                           |
| C→M               | `{"type":"status","status":"paired"}` (after the browser confirms)                                                                                                                                                                                                                                                                                                                                                                                                           |
| C→M               | `{"type":"req","id":"<string>","op":"<op>","args":{…}}`                                                                                                                                                                                                                                                                                                                                                                                                                      |
| M→C               | `{"type":"res","id":"<same>","ok":true,"result":{…}}` or `{"type":"res","id":"…","ok":false,"error":{"code":"not_found"\|"invalid"\|"forbidden"\|"unavailable"\|"backend"\|"unsupported","message":"…"}}`                                                                                                                                                                                                                                                                    |
| M→C               | `{"type":"event","sessionId":"…","epoch":"…","seq":123,"rootSessionId":"…","event":Event}` — pushed for **every** session of the machine; Cerea fans out to watchers of the session and of its root, and drops the rest. `rootSessionId` is the top-level ancestor (the session itself for a top-level session); a child session's envelopes therefore reach its root's watchers mid-turn, which is what surfaces subagent approvals and questions in the parent's view (§7) |
| M→C               | `{"type":"credential","state":"ok"\|"expiring"\|"expired","detail":"…"}` — the gateway/enrollment credential's health (replaces regex-matching `lastError`, review C9). `expired` = refresh got `invalid_grant`; the machine sends it before its socket dies so Cerea can record it on the device row and show the re-enroll card                                                                                                                                            |
| M→C               | `{"type":"auth","token":"…"}` (renewal, §3)                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| M→C               | `{"type":"call","id":"<galopin-unique>","op":"schedule.<x>","sessionId":"<caller>","rootSessionId":"<its root>","caller":Caller,"args":{…}}` — a machine call (below)                                                                                                                                                                                                                                                                                                        |
| C→M               | `{"type":"callres","id":"<same>","ok":true,"result":{…}}` or `{"type":"callres","id":"…","ok":false,"error":{"code":"invalid"\|"forbidden"\|"not_found"\|"limit"\|"unavailable"\|"unsupported","message":"<a sentence the model can read>"}}`                                                                                                                                                                                                                                |

Unknown frame types and unknown event kinds are ignored by both sides (forward compatibility); unknown ops answer `unsupported`.

**Machine calls (M→C `call`, C→M `callres`).** The one request the machine makes of Cerea, used by the schedule tools (§6 "Agent tools"). `id` is unique per galopin process; `caller` is `Caller = {"workspaceId":"…","permissionMode":"deny"|"ask"|"allow","coordination":["session_list",…]}`, the calling session's facts as galopin knows them (the root's selector word and coordination grant; the session's workspace id as `workspace.list` reports it). Cerea acts as the device's owner, on this device only, and answers an unknown `op` `unsupported`. galopin sends a call only while the link is up **and paired** (otherwise the tool answers that Cerea is unreachable), fails every pending call when the connection drops, and times a call out after **20 s** as `unavailable` — which is also what a Cerea that predates calls produces, since it ignores the unknown frame type. A `callres` for an id nobody is waiting on is dropped. Galopin uses a family only when the welcome listed it in `features.machineCalls`; against a Cerea without `schedule` the tools answer "this Cerea does not support schedules from agents; update it". The ops (`args` → `result`):

- `schedule.context {}` → `{"scheduledRunOf":"<scheduleId>"|null,"enabled":bool}`: whether the caller's session or its root is a session a schedule's run created or targeted.
- `schedule.list {}` → `{"schedules":[{id,name,recurrenceText,timezone,paused,status,nextRunAt,lastRunAt,workspace,session:"new"|"<sessionId>",permissionMode,coordination,createdBy:{kind:"person"}|{kind:"agent",sessionId,title},self}]}`: this device's schedules of the owner; `self` = the caller's session is a run of it. Prompts included.
- `schedule.create {name, prompt, recurrence, timezone?, workspaceId?, session:"new"|"this", permissionMode, agentMode?:"plan"|"build", coordination?}` → `{schedule}`. `agentMode` defaults to `"build"` and is not bounded by the caller. `coordination` is stored as two options: `session_list`+`session_read`+`session_send` all together or not at all, and `session_spawn` on its own (a partial set is refused). `recurrence` is Cerea's `recurrenceSchema`: `{type:"hours",every}` \| `{type:"daily",at:"HH:MM"}` \| `{type:"weekdays",at}` \| `{type:"weekly",day:0-6,at}` \| `{type:"cron",expr}`. Defaults: the owner's saved timezone (else UTC); the caller's workspace; `"this"` is the caller's ROOT session.
- `schedule.update {id, …any create field but session…, paused?}` → `{schedule}`; `schedule.delete {id}` → `{}`.

List items also carry `prompt`, `recurrence`, `agentMode`, optional `lastStatus`/`disabledReason`; `status` is `"active"|"paused"|"disabled"`, `workspace` is `{id,name}`, times are ISO strings or null. A malformed call with an id is answered `invalid` at once, an unpaired machine `forbidden`; with the kill switch off `schedule.context` answers `enabled:false` and the other ops `unavailable`. Pause-only updates and deletes are never refused by Cerea's rate limit (they still count).

Cerea enforces the store's rules (15-minute floor, per-user cap, kill switch), the device, `permissionMode` no looser than the caller's, `coordination` ⊆ the caller's, at most 5 active agent-created schedules and 10 changes an hour per device; a refusal is `forbidden`/`limit`/`invalid` with a sentence galopin hands to the model.

`Backend = {"id":"opencode","version":"1.18.32","capabilities":{"diff":true,"children":true,"usage":true,"compact":true,"images":true,"files":true,"worktrees":false,"questions":true,"revert":true,"revertFiles":true,"efforts":true,"commands":false,"toolImages":true,"agentTools":true,"coordinationGrant":true,"steer":true,"permissions":true,"scheduleTools":true}}` — `commands` is probed, never versioned: opencode advertises it only when its own `GET /doc` lists the `session.command` operation (cached per process, re-probed after a supervised restart); ACP reports it always, its `available_commands_update` carrying the list per session. `toolImages` means tool parts list the images their calls produced and `session.attachment` (§6) serves them: opencode and ACP both report it; a machine older than this field omits it, and Cerea then renders no tool images. `agentTools` means galopin has installed its own agent-coordination tools into the backend (§6, "Agent tools"): opencode reports it, ACP never does. `coordinationGrant` means `session.grantCoordination` (§6 "Permissions") works: the tools are installed **and** the session's rules are galopin's to compose; a galopin older than the op omits it and answers the op `unsupported` (the usual unknown-op path), so Cerea reads absent as `false`. `steer` means a `session.prompt` sent while the session's turn is running is accepted and folded into the running turn rather than refused (opencode: `prompt_async` queues it server-side; ACP refuses it, §6 `session.prompt`); a machine older than either field omits it, read as `false`. `scheduleTools` means galopin installed the schedule tools (§6 "Agent tools", reaching Cerea through machine calls, §5); reported with `agentTools`, absent from an older galopin. `permissions` means the Deny / Ask / Allow selector (`session.setPermissionMode`), `permission.rules` and `permission.saved.remove` (§6 "Permissions") work on this backend (opencode only). The old `autoAccept` capability is gone; a machine older than this change still sends it, and a panel ignores it.
`Policy = {"autoAccept":"denied","permission":{"max":{"bash":"ask"}},"workspaceRoots":[],"allowFreeModels":false}` — `permission` is §4's. `autoAccept` is the constant `"denied"` (auto-accept no longer exists); Cerea's hello schema still requires the field, so it is sent for one more release and then dropped. There is no `permission.responders`. `permission.max` is how the panel knows what a session's Allow still cannot do (it names the capped key, e.g. "Allow · bash asks (machine limit)") and that an "always allow" on that key stores nothing.

With the machine powers (§9), `hello` also carries `"machine":Machine`, and `Policy` gains the power fields:
`Policy = {…, "files":"read", "fileWrite":"denied", "fileDeny":[…], "terminal":"denied", "maxTerminals":8}`
`Machine = {"capabilities":{"files":true,"fileSearch":true,"fileWatch":false,"fileWrite":true,"terminal":true}}`: a capability means "this galopin implements it on this OS", and the policy means "the owner allows it"; both must hold. `terminal` is false on non-Unix builds. Two more frame shapes exist only there: `notice` (§9.5) and binary terminal frames (§9.2). Two more error codes: `"conflict"` (`files.write` revision mismatch, `error.details = {revision}`) and `"too_large"` (over a cap).

**Worktrees.** `workspace.create`'s `worktree` form runs `git worktree add -b <branch> <path> <base|HEAD>` against the workspace named by `from`, using the git CLI directly rather than opencode's experimental `/experimental/worktree` — worktrees are a property of the checkout, not of one backend. `path` is `<repo parent>/<repo name>.worktrees/<branch>` (`git rev-parse --show-toplevel` finds the repo root regardless of whether `from` points at the root or a subdirectory); `branch` is refused if it contains `".."` or is otherwise unsafe as a path component. The resulting directory is registered as an ordinary workspace, still subject to `workspaceRoots`, carrying `{worktreeOf: from, branch}`. `workspace.archive`'s `removeWorktree` runs `git worktree remove` (`--force` when `force` is set); git itself refuses a dirty worktree without `force`, so there is no separate dirty check. Archiving without `removeWorktree` just hides the workspace, same as any other — the directory and the git worktree both remain on disk.

**Permissions (capability `permissions`).** opencode owns every tool permission; Cerea shows its asks as cards and relays the answers (`permission.reply`). galopin adds what opencode cannot know — the machine's own rules and its ceiling (§4), and a per-session **selector** a person sets — and keeps only what opencode cannot own: the approvals of `session_read`/`session_spawn`/`session_send` and the non-permission limits (hop, rate, same-workspace) of §6 "Agent tools". Cerea can read the rules (`permission.rules`, which also lists the session's `coordination` grant), set a session's selector (`session.setPermissionMode`), grant its coordination tools (`session.grantCoordination`) and remove an exception (`permission.saved.remove`). It can write no ceiling and no policy, and **no selector, exception or reply can make a session more permissive than the ceiling**: the ceiling is composed last.

**The selector: Deny / Ask / Allow.** One word per top-level session, covering the whole session until it is changed; **new sessions start on Ask** — existing sessions on upgrade, and sessions on a machine whose `policy.json` predates permissions too, so such a machine asks before it writes **without a re-enroll**. A session a spawner starts inherits its spawner's word instead (`session_spawn` below); `permission: "ask"` pins one stricter. The word moves what follows it; what is **untouched** keeps the agent's own rules under all three words: `read` (including its `*.env` asks), `glob`, `grep`, `list`, `lsp`, `question`, `todowrite`, `todoread`, `plan_enter`, `plan_exit`, `skill`, `external_directory` (opencode's own safe-directory allows included) and `doom_loop`. So reading stays allowed, the question tool works with no card, and under Allow two asks survive: a write outside the project folder and the stuck-agent brake. Everything else follows the word: `edit` (write and patch), `bash`, `webfetch`, `websearch`, `codesearch`, `task`, every MCP tool and every custom tool. **A deny is never moved**: a rule that denies (the agent's — plan's `edit`, a read-only subagent's `*: deny` — the file's, or the machine's) stands under every word, since a bare `* : ask` would turn it into a question. **Under Deny the blocked tools are missing, not refused**: opencode drops a tool whose every pattern is denied from the model's tool list, so the model is never told why it has no `bash`. galopin therefore adds to every prompt of a session on Deny an extra system prompt for that turn (`prompt_async`'s `system` field, never part of what the person said and never shown) saying which tools are switched off and asking the model to say what it would run and ask for Ask or Allow, rather than reaching for another tool. A live canary (`TestSelectorS12…`) lists the permission names opencode 1.18.32 knows and fails on one that is in neither set.

**Exceptions.** "Always allow" on a card is a per-session exception for that command or pattern, on top of the word: `{id: "ex_…", permission, patterns, grantedAt}` on the ROOT session, listed by `permission.rules` as `savedApprovals` (each `removable`) and removed by `permission.saved.remove`. Under Ask and Allow an exception sits after the mode block, so it wins; under Deny it sits before, so **Deny wins** — the exception is kept while blocked and comes back when the word does. A subagent has no selector or exceptions of its own: its rules are its **root's** word and exceptions over the child agent's rules, capped, never the machine's own allows. They are applied when the child appears and re-applied to every tracked subagent whenever the root's word or exceptions change.

_When a change takes effect._ opencode takes a session's rules **when a turn starts** (probed live on 1.18.32: a mode changed while a turn waited on an ask did not apply to the turn's next step). So a change to the word or an exception is in force **from the session's next turn**; a turn already running finishes under the rules it began with, and **a change never stops, cancels or interrupts it** — by decision, not by omission: switching to Deny or Ask while the agent works does not abort the turn, so what it is already doing is not undone, and the next prompt is the first to run under the new word. A client should say so when it sets the word on a busy session ("applies from the next message"). **A new subagent's first turn is the exception, whatever the word.** A task creates its subagent session and starts its first turn in one step, with the rules the session was created with (its parent's denies and `external_directory` rules, and its agent's); nothing can be put on it in time, however fast. That first turn is therefore judged by the **agent-level floor** (below), which asks for the names the word moves (`edit`, `bash`, `webfetch`, `websearch`, `codesearch`, `task`) even under Allow; galopin reads each such ask against the rules the child is entitled to (its root's word and exceptions under the ceiling) and answers it `once` when they allow it (see "Auto-accept is gone" below). So under Allow nothing waits except keys the ceiling caps; on Ask, the ask is an ordinary card. Later turns of that child session (a `task_id` resume, a message sent to it) are judged by the root's word and exceptions as they stand then; galopin promises no more than that, and cannot steer which agent a task starts (opencode lists every agent type to the model whatever the session's rules, pinned by `TestUpgradeCanaryTaskListIgnoresTheSessionsTaskDenies`). A client may mark a card that does reach a person from such a turn "New subagent · first turn asks" (an ask whose session is a subagent that has not yet finished a turn).

_Precedence_, lowest to highest, as opencode resolves it (the last matching rule wins; verified against 1.18.32 by the `TestUpgradeCanary*` specs): opencode's built-in defaults, the static `opencode.json` (`enroll` writes `edit`/`bash`/`webfetch: ask` into it for a new machine; an existing machine's file is untouched), the agent's own rules, then **the session's rules**, which galopin composes in this order: (1) the machine's own rules; (2) the **mode block**: `* : <word>`, then every rule beneath restated with an allow or ask taken to the word and a deny left alone, then the untouched set restated as the agent has it (an `ask` base first, for a name nothing mentions); under Ask and Allow the session's **coordination grant** (below) and then the machine's own rules for galopin's four coordination tools are re-appended (the machine's rule is its explicit consent, and it comes after the grant so an owner's ask or deny for a tool still beats a caller's grant); (3) the exceptions, one `allow` per pattern; (4) the **ceiling's tail**, last. The in-memory "always" approvals opencode keeps are checked after all of them and are shared by every session in the workspace; galopin no longer creates any, but a tightened ceiling still restarts opencode so that none held by an older process outlives it.

_How they are applied._ (1) At `session.create` the session is created **with** its rules, so none of them arrives after the first prompt can exist; before every prompt or command galopin re-sends them only if they differ from what the session last got (a fingerprint kept with the mode/model overlay, so a restart of galopin does not grow the list — opencode only appends, and each block starts with `* : <word>` so a later block beats an earlier one for every input), and a prompt whose rules cannot be applied is not sent: it needs opencode's agent rules, since the block is restated over them. The ceiling is applied **as a cap**: for each capped key, the rules already in force restated for that key and lowered to the ceiling, so the tail's last match is `min(what was in force, ceiling)`. (2) galopin never sends the deprecated `tools` map, which replaces a session's rules wholesale, and strips it from every body it builds. (3) An `always` is answered `once` and becomes an exception (above). (4) When the ceiling or the machine's rules **tighten** (`galopin policy set`, picked up from `policy.json` within seconds; a loosened or unparsable file is ignored), galopin restarts opencode, withdraws the asks that died with the old process (`permission.replied {decision:"reject"}` / `question.resolved`), and re-applies every session's rules; exceptions are galopin's own and are kept. (5) **The agent-level floor**: `OPENCODE_CONFIG_CONTENT`, rebuilt from `policy.json` at every start of opencode, restates the ceiling as rules for the built-in agents and, for the subagents `general` and `explore`, the machine's own `ask`/`deny` rules as caps **and the names the selector moves as `ask`** (`edit`, `bash`, `webfetch`, `websearch`, `codesearch`, `task`, for an agent that grants them), because a subagent session is created by opencode, inherits only its parent's **denies** and `external_directory` rules, and falls back to its agent's rules (`general` is `"*": allow`). A floor `ask` is written only for an agent that grants the key by default (a table of the built-ins, checked against the live binary), and the read-only `plan` and `explore` get their `edit` deny re-asserted so the static `edit: ask` cannot soften them. As soon as a subagent's session event appears, galopin gives it its root's word and exceptions and the ceiling as session rules, using the agent opencode names in the child's title (`… (@general subagent)`) until the parent's `task` call confirms it (denies only if unknown), and **the machine's own restricting rules** as further caps — never the machine's own allows. That cannot land before the child's first turn starts (above), so the floor holds that turn, and the rules are in force for the child's later turns.

_`session_read` / `session_spawn` / `session_send`._ They have no opencode permission, so galopin looks the tool's name up in the asking session's rules (the agent's, then the session's; the machine's own rule for the name survives the selector under Ask and Allow, and Deny refuses): `allow` → no card unless the spawn is an escalation (the result carries `autoApproved:true`, the badge reads **allowed by the permission rules**), `deny` → refused with no card and none of the rate budget spent, `ask` or no rule → a `gp_` card. A **wildcard allow never grants a read** — opencode's default `"*": allow` would otherwise let any session read any transcript — **but under the Allow word it grants a spawn or a send**, like any other tool (the reads stay grant-gated because a transcript can hold secrets) — while a wildcard deny refuses them. An allow does not lift the hard limits: a send or a read into another workspace, or a send at hop 4 or more, is still carried by a card; the per-pair rate limits still refuse. "Always" on a `gp_` card is "once" and the card offers none; the Allow word never answers one.

_Coordination grant (`session.grantCoordination`, capability `coordinationGrant`)._ A scheduled run has nobody to answer a card, and no op can write a rule (`session.setRules` is retired), so the grant is the one narrow thing a client may write: `{sessionId, keys}` with `keys` drawn from `session_list`, `session_read`, `session_send`, `session_spawn` and nothing else (`invalid` otherwise, nothing recorded). galopin keeps it on the ROOT session inside the same record as the selector (the session overlay, `coordination`), so it **survives a restart** like an exception does, and composes it as one `allow` per key **after the mode block and before the machine's own rules for the tools** — and so beneath the ceiling's tail, which is last. What that makes of it:

- **the machine's ceiling is never exceeded:** a key capped at `ask` still asks (its `gp_` card is raised), at `deny` it is refused (opencode then also drops the tool from the model's list); an owner's own `ask`/`deny` rule for the tool beats the grant too;
- **the hard limits stand:** a `session_send` or `session_read` into another workspace still asks, a send past hop 3 still asks, and the per-pair rate limits (five a minute, send and read each) still refuse;
- **Deny wins:** under the Deny word a grant is kept but not applied (as an exception is), and returns with Ask or Allow;
- **a subagent follows its root's grant**, under the child ceiling, like the selector;
- `session_list` needs no approval today, so granting it changes nothing yet; it is accepted so a grant can name the whole set;
- `keys: []` clears the grant; a later grant replaces an earlier one entirely (a later block beats an earlier one, so nothing of the old grant stays in force). `permission.rules` lists it as `coordination`.

Like the selector it applies from the session's **next turn**: a turn already running keeps the rules it began with.

_Audit._ Every reply is `permission {session, requestId, tool, decision, by:"user"}`, never a pattern. A mode change is `permission.mode {session, mode}`; a coordination grant, a clear and every refused attempt is `session.grantCoordination {session, keys, outcome}` (`outcome` is `ok`, `invalid`, `not_found`, `unsupported` or `failed`); removing an exception is `permission.saved.remove {session, id}`. A tightened policy is `permission.tightened {restarted}`.

_The residual, stated plainly._ A hijacked session may loosen its own rules **up to the ceiling** and never past it: the ceiling is composed last on every apply, "always allow" is capped by it, and nothing else writes session rules. The one hole is `bash`: if the ceiling lets bash run, the agent can read opencode's server password from its own environment and PATCH its own session's rules directly, past the ceiling. That is why `enroll` defaults `bash` to `ask`: an owner who wants unattended bash raises it deliberately (`--permission-max bash=allow`), and a session on Allow then runs bash with no card. Spawns carry no such default: a spawn is bounded, audited with both sessions, and capped by the same ceiling as its caller — so fresh machines spawn with no card on Allow, while `bash` keeps asking per command until the owner raises it. Machines enrolled before this default keep `session_spawn=ask` in their own file; re-enroll adopts the new one.

**Agent tools (capability `agentTools`).** Four tools galopin installs into opencode itself — `session_list`, `session_read`, `session_spawn`, `session_send` — so the model of one session can coordinate with other sessions **on the same machine**. They are _tools the model calls_, not new `req.op`s: Cerea sends nothing new, and what it sees is ordinary session, message and permission traffic carrying the fields below. (They are opencode custom tools, one file each in a directory galopin owns and passes as `OPENCODE_CONFIG_DIR`; a tool's `execute(args, ctx)` receives `ctx.sessionID` and calls galopin's own loopback endpoint, bearer-authenticated with a per-process random token that only opencode's environment holds. A local MCP server is **not** a route: verified against 1.18.32, an MCP `tools/call` carries only `{name, arguments, _meta.progressToken}` and nothing that names the calling session.)

**Galopin owns the approval.** opencode runs a custom tool without asking anything, so `session_read`, `session_spawn` and `session_send` do not depend on opencode's permission system at all: the tool call blocks inside galopin's loopback handler, galopin emits its own `permission.asked` for it (below), and, unless the machine's rules allow it ("Permissions" above), the call proceeds only when a person answers `permission.reply` with `once` (`always` is treated as `once` — nothing is ever remembered). The request `id` is minted by galopin and has the prefix `gp_`; a `permission.reply` on such an id resolves galopin's held call and never reaches opencode. Once raised it is **never answered for a person, whatever the session's Deny / Ask / Allow word** — by a check on the request itself (`metadata.galopin == true`, id prefix `gp_`), not on the tool's name. `reject`, or the session's turn being cancelled while the ask is pending, makes the tool return a refusal text to the model; a cancelled turn also closes the held ask with `permission.replied {decision:"reject", by:"user"}`. `session_list` only reads, needs no approval and is audited.

**Rule-based approval (decided before the ask).** Galopin decides BEFORE it raises the ask, and when the machine's rule says allow no `gp_` ask exists at all — nothing is replied, so the never-answered-for-a-person rule above is untouched. The decision is the machine's rule for the tool name, read from the asking session's rules (§6 "Permissions"): allow → no card, deny → refused, ask or absent → card. Auto-accept has no part in it: what decides is the machine's rule for the tool name, and under the Allow word that includes the blanket — a session on Allow gets no card for a spawn or a send the ceiling and the machine's own rules leave alone, and it still gets one where a rule or the ceiling asks, like any other tool. A spawn needs no target check: the child inherits the caller's word (`permission: "ask"` pins it stricter), and a mode that could be an escalation always shows the card (below). A send borrows the target's powers, so an allow does not cover a target in another workspace or a hop past 3: those ask. **Questions are never approved this way.** `enroll --no-agent-tools` (and `galopin policy set --no-agent-tools`) still turns the tools off entirely.

_Hop and rate._ (A read has no hop: it moves no instruction between sessions, and its rate limit is the same five a minute per ordered reader→target pair, counted apart from sends.) A send at hop 4 or more is **not refused**: it falls back to the approval card (`hop` in its metadata keeps counting; an allow rule applies only within hops 1–3), which is what lets two sessions carry on a long exchange with a person clearing it every step. The per-pair rate limit is unchanged and stays a **hard refusal** — it is the loop brake, under an allow rule or not.

_Visibility._ A call the machine's rules allowed is audited as `agent_tool {tool, from, decision:"allow", reason:"rule"}` (a spawn's `to` is on the `done` row that follows, whose `reason` counts the exceptions it inherited, when any) and the tool result carries `"autoApproved": true` (a spawn's `{"sessionId","title","mode","autoApproved":true}`; a send's `{"autoApproved":true}` in place of `{}`), which Cerea renders as an **allowed by the permission rules** badge (it is set only when the rules said allow and no card was raised — nothing answers a `gp_` ask for a person, so nothing else can set it) on the sender's "Spawned …" / "Sent to …" card. A denied call is `refused` with the reason. The approval card itself is unchanged when it is shown.

_The residual, stated plainly._ Where a rule allows a send, the sender can message peers in its workspace without anyone seeing a card. That exposure is noise, and a peer session's context being steered by another agent's text; it is bounded by the hop and rate limits (a chain past 3 hops needs a person; five sends a minute per pair) and it is never invisible: every one is an audit row and a badge. It is also the owner's explicit rule, not a side effect of a session's flag.

The approval card is the existing `PermissionRequest`, filled in like this:

```
session_spawn: {id:"gp_…", sessionId, tool:"session_spawn", title:"Start a new session: <title>", callId, messageId,
                patterns:[], always:[],
                metadata:{galopin:true, title, modeId, modelId|null, workspaceId, prompt, permissionMode}}
session_send:  {id:"gp_…", sessionId, tool:"session_send", title:"Send a message to <target title>", callId, messageId,
                patterns:[], always:[],
                metadata:{galopin:true, target:{sessionId, title, workspaceId}, text, hop}}
session_read:  {id:"gp_…", sessionId, tool:"session_read", title:"Read messages from <target title>", callId, messageId,
                patterns:[], always:[],
                metadata:{galopin:true, target:{sessionId, title, workspaceId}, last}}
```

`prompt` and `text` are shown in full, up to 8 KiB; a longer one is refused before any ask is raised, so a card never shows a truncation the model did not make. `modeId` is the mode the child will actually get, `permissionMode` the word it will start with. Every tool call, allowed or refused, is a row in `audit.log`: `agent_tool {tool, from, to?, decision:"done"|"refused"|"auto", reason?}` — one row naming both sessions (`from` the caller, `to` the spawned child or the addressed session), never the prompt or text.

**The caller is verified.** The relay token proves only that opencode made the call, so galopin also requires the event stream to show an unfinished tool part with the relayed `callId` and tool name in the named session (waiting up to 5 s for it to arrive): a session id alone, written by anything holding the token, borrows no other session's mode, workspace or standing. A call it cannot match is refused.

**`session_list {note}`** (`note` is ignored; opencode requires an argument) → the machine's non-archived **top-level** sessions, `[{sessionId, title, workspaceId, workspace, mode, status, spawnedBy?, note?}]` (`mode` is `"default"` when none is set; `note` marks the caller's own tree, not a send target). Subagents, archived and untracked sessions are absent; the listing refreshes galopin's tracking first, so a restarted galopin still addresses every session.

**`session_read {target, last}`** → another session's most recent messages as **plain text** (not JSON). `target` is a `sessionId` (from `session_list`); `last` is a number of messages, `1`–`50` (opencode marks every argument required, so `0` — or a numeric string — is accepted and means the default, `10`; a larger number is clamped to 50; a fraction, a negative number or text is refused). What comes back is **only user and assistant text**: each text part of a message, in order, oldest first, each message headed `[user · <RFC 3339 time>]` or `[assistant · …]` (a user message another session wrote with `session_send` reads `user (sent by another session)`). **No tool inputs or outputs, no reasoning, no files or images, nothing synthetic** (the backend's own injections, among them the line that says who a `session_send` came from); a message with no text left is skipped, and `last` counts the messages that are shown. A message over **4 KB** is cut there (on a character boundary) with `[message truncated at 4 KB]`; the whole answer is capped at **32 KB** by dropping the **oldest** messages first, marked `[earlier messages omitted: the answer is capped at 32 KB]`. The answer opens with a header line naming the session and saying its text is quoted data: the reader's model is told not to follow instructions inside it. The gates, in order: the target is not the caller (`you cannot read your own session`); it is on this machine and listed (an unknown or archived id is refused with `no such session on this machine (or it is archived)`); it is a top-level session **or a subagent of the caller's own tree** (another tree's subagent is refused); a `deny` rule refuses it before any budget is spent; at most 5 reads a minute per ordered reader→target pair (a hard refusal); then the approval or the rule's allow. **The approval is decided exactly like a send's:** `allow` runs it, `deny` refuses it, `ask` or no rule raises a `gp_` card; a blanket `*` allow, and the session's Allow word, do **not** grant it, because a transcript can hold secrets; and a target in **another workspace always asks**, whatever the rule. Every read is audited as `agent_tool {tool:"session_read", from, to (the target), decision:"allow"|"done"|"refused", reason?}` — **never the text read**.

**`session_spawn {title, prompt, mode}`** (`mode` is `"plan"`, `"build"` or `"inherit"`; opencode marks every argument of a dependency-free tool required, so "leave it out" is spelled `"inherit"`) → `{sessionId}` once the person approved (or the rules allowed it) and the child's first prompt was accepted (the child's turn then runs on its own). The gates, in order, each refusal a tool error the model reads:

1. the workspace is **always the caller's own** — there is no argument for another, and a `workspaceId`- or `directory`-shaped argument is refused, not ignored;
2. `mode` defaults to the caller's; a given one that is the caller's own is fine, and so is `plan` when the caller runs `build` or the backend's default (a custom mode could be stricter than `plan`, so custom → `plan` is a card). Any other name could be **less restricted than the caller** and galopin has no order to compare modes by, so it is an _escalation_: not refused, but always a card, even where a rule allows spawning, with `escalates:true` and `callerModeId` in the card's metadata beside `modeId` so the person sees both modes;
3. the model is the caller's, under the `allowFreeModels` gate exactly as `session.setModel`;
4. the child inherits its caller's permission word, coordination grant and exceptions, never more (an Allow spawner makes a child that runs without a card; a read-only child comes from `mode: "plan"`) — still under the machine's ceiling, which the rules re-apply caps last. The exceptions are the caller's root's "always" answers, copied as they are (same permission and patterns, each applied with `AddException`), for an Ask caller too; a failure to copy refuses the spawn. **Later changes are not propagated**: removing an exception from the caller leaves the child's copy in place. The child is a new **top-level** session (`parentId: null`), not a subagent; backends without a selector (ACP) keep their own default;
5. fork-bomb limits: a spawn chain at most 2 deep (`spawnedBy` links; a session at depth 2 cannot spawn), at most 3 live (not archived, not finished) spawned sessions per root, at most 6 spawn attempts per root per 10 minutes — all refused before an ask is raised, so a looping model cannot flood the card list;
6. then the approval; then the child is created with its `spawnedBy` marker (§7) and prompted.

**`session_send {target, text}`** → `{}` (`{"autoApproved":true}` when the machine's rules allowed it) once the person approved (or the rules allowed it) and the target accepted the prompt. `target` is a `sessionId` from `session_list`. The gates, in order: same machine only (an id galopin does not list is refused); the target is a non-archived **top-level** session; **no self and no same-tree sends** (the target's root is the caller's root: yourself, your subagents, your ancestors, your siblings — use `task` for those); `hop` — the sender's current hop (the `sentBy.hop` of the message that started its running turn, else `0`) plus 1 — above 3 the send is asked (an allow rule does not cover it, and it is never refused for hop alone); at most 5 sends per minute per ordered sender→target pair (a hard refusal); a `deny` rule refuses it before either budget is spent; then the approval, or the rule's allow (above); then delivery as an ordinary prompt (opencode `prompt_async`), so a **busy target folds it into its running turn** (capability `steer`) instead of queueing behind it. The message the target sees carries `sentBy` (§7), and its text names the sender, so the target's model never mistakes it for its person.

**Result shapes (pinned).** A tool part's `output` on success: `session_spawn` → a JSON object `{"sessionId", "title", "mode", "permissionMode"}` (`sessionId` is the contract, the rest informative — `permissionMode` is the word the child actually started with; plus `"autoApproved": true` when auto-approved); `session_send` → exactly `{}`, or `{"autoApproved":true}` when auto-approved; `session_read` → the plain transcript text above (an auto-approved read is told apart by its audit row, `decision:"allow"`, not by a marker in the text); `session_list` → the JSON array above. Every refusal — any gate above, a declined approval, an internal failure, an aborted call — makes the tool part `status:"error"` and its `error` text **exactly a JSON object `{"refused": "<reason>"}`** (`reason` is plain prose for the model and the person; never parse it further). A cancelled turn's held call ends the same way. So a client reads one shape: `status:"completed"` → success shape above, `status:"error"` → `JSON.parse(error).refused`.

Refusals never touch the wire beyond that: no new error codes and no new ops. A machine without `agentTools` simply has no such tools.

**Schedule tools (capability `scheduleTools`).** Installed with the others: `schedule_list {note}`, `schedule_create {name, prompt, recurrence, timezone, workspaceId, session, permissionMode, coordination}` (opencode marks every argument required: `""` means the default, `[]` no coordination), `schedule_update {id, changes:{…fields, paused?}}` and `schedule_delete {id}`. Each is a machine call (§5) after galopin's own gate; the result is Cerea's `result` as JSON (plus `"autoApproved":true` when no card was shown), a refusal the usual `{"refused":"…"}` with Cerea's sentence. Permission key **`schedule`**, for the three mutating tools both as a machine rule and as a ceiling key (default uncapped; `--permission-max schedule=ask|deny`). Unlike the `session_*` tools, **the blanket Allow covers it**: under Allow the session's rules are read as they are (`*: allow` included), under Ask or Deny a wildcard allow says nothing, and the machine's own `schedule` rule is re-appended after the mode block like the coordination tools'. The decision, first match wins:

| Call                                                                                        | Result                                                       |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| ceiling `schedule: deny`                                                                    | refused (all four tools, list included)                      |
| `schedule_list`                                                                             | no card                                                      |
| the machine's own rule `schedule: deny`                                                     | refused                                                      |
| ceiling `schedule: ask`                                                                     | card (even a run stopping itself)                            |
| `schedule_update {paused:true}` alone, or `schedule_delete`, of a schedule with `self:true` | no card ("stop when done"), **under the session's Deny too** |
| the session's word reads deny (Deny)                                                        | refused                                                      |
| `schedule_create` from a scheduled run (`schedule.context.scheduledRunOf` set)              | card, even under Allow or an allow rule (runaway guard)      |
| `schedule_create`, rule allow                                                               | no card                                                      |
| `schedule_create`, otherwise                                                                | card                                                         |
| any other update or delete                                                                  | card, even under Allow                                       |

So that a run on Deny can still stop itself, the Deny composition keeps `schedule_list`, `schedule_update` and `schedule_delete` visible to opencode (one `ask` rule each after the mode block; opencode never asks for a custom tool, so the rule only keeps the name) while every other tool, `schedule_create` included, stays hidden. The tool arguments add `agentMode` (`"plan"|"build"`, `""` for the default) to create and to `changes`.

Refusals that do not depend on Cerea's answer happen before Cerea is asked anything; mutating calls are rate-limited to 5 per root session per 10 minutes, counted before the card. The card (`tool` = the tool's name, `metadata.galopin:true`, `metadata.reason`): create → `metadata.schedule = {name, recurrence, recurrenceText, timezone?, workspace:{id,name}, session:"new"|{sessionId,title}, permissionMode, coordination?, prompt}` and `scheduledRun:true` from a run; update → `metadata.schedule = {id, name, recurrenceText, self}` and `metadata.changes` (the changed fields, prompt in full); delete → `metadata.schedule`. Audit: `agent_tool {tool, from, decision, reason?, schedule}` where `schedule` is the id (or a new schedule's name); never the prompt.

**Background subagents (opencode 1.18.32, `Policy.backgroundSubagents`).** opencode's own `task` tool — not galopin's `session_*` tools above — gains `background:true` behind `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`, which galopin sets only when the machine allows background subagents (the enroll default; `--no-background-subagents` denies them) (denied strips any inherited value, so `background:true` fails closed with "Background subagents require OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true"). No new spawn path and no `session_spawn` change: with `background:true` the child keeps running after its parent turn ends and opencode injects the result back as a synthetic text part `<task id state><summary>…</summary><task_result|task_error>…</…></task>` on the parent; `task_id` follows up that same running child (a follow-up, never a new spawn); `POST /experimental/session/:id/background` ("Background subagents") detaches a blocking synchronous child into the same state. Children stay in the same exposed tree (`session.children`, `parentId`, `rootSessionId` fan-out) — the only new shapes are the task tool's `output` carrying `<task … state="running">` and the synthetic completion part, which Cerea folds into one visible parent marker per child (running, then completed or failed) rather than model text. The marker says only what opencode reported: a `task_id` resume reads as a follow-up, and the injected result reads as automatic.

## 7. Events (the normalized stream)

Envelope: `{sessionId, epoch, seq, rootSessionId, event}`. `epoch` is a random id minted when the agent process starts (its in-memory buffers are lost on restart, so a new epoch means "resync from snapshot"). `seq` is per session, starts at 1 in each epoch, strictly increasing, no gaps. `rootSessionId` is the top-level ancestor of `sessionId` (itself for a top-level session); the materializer learns the parent edge from `Session.parentId` (tracked sessions, `session` events, `session.children`) and from the parent's own task/subtask parts naming the child they spawned. Identity-based dedup is on `(epoch, seq)` only, never on content (R3/R4).

**Auto-accept is gone.** There is no responder: galopin never answers an ask for a person, with one exception — a **subagent's** ask the rules it is entitled to allow (its root's mode and exceptions under the ceiling, `ChildRules`). A task starts the child's first turn before galopin can give the session its rules, so that call is asked by the agent-level floor whatever the root's word; galopin reads the ask against the entitled rules and answers `once` (audited `by:\"galopin\"`) when they allow it. Under Allow with the ceiling not capping the key, no ask is left standing; a root on Ask, or a capped key, still waits for a `permission.reply`. Every other `permission.asked` the machine raises reaches the client and waits for a `permission.reply`. What used to be the auto-accept toggle is the per-session Deny / Ask / Allow selector (§6 "Permissions"), which decides which tool calls ask at all (opencode never raises an ask for what the word allows or denies) rather than answering asks for a person.

`Part = {id, messageId, role, type, …}` by `type`:

- `text` `{text, synthetic?: bool}` (synthetic parts are backend-injected; Cerea does not show them as user text — except a background task's `<task>` result injection, which folds into that child's parent marker as completed or failed, labelled automatic)
- `reasoning` `{text}`
- `tool` `{callId, tool, status:"pending"|"running"|"completed"|"error", title?, input{}, output?, error?, attachments?: ToolAttachment[]}` — `attachments` (capability `toolImages`) lists the images the call produced, by reference and never with bytes: `ToolAttachment = {sha256, mime, size, filename?}`, `sha256` the lowercase hex digest of the _decoded_ image computed on the machine, `mime` one of `image/png|jpeg|gif|webp`, `size` the decoded byte count, at most 8 per call, each at most 8 MiB; the part's `attachmentsOmitted` (int, omitted when 0) counts the images it produced that are not listed (over the cap or size, or not a raster type), so a card can say so. Nothing else is listed — SVG, non-`data:` URLs and non-image parts are dropped machine-side. The list rides the part like any field, so a snapshot (`session.sync`, a reload) and the live `part` event carry the same one; bytes come from `session.attachment` (§6) only. **opencode:** (galopin reads the event stream with a bounded line reader — 128 MiB — because a tool part carries its images inline in one line; a longer line is skipped without dropping the stream and its session is resynced from the transcript, tool parts re-announced) the completed tool state's `attachments` (image `FilePart`s whose `url` is a `data:` URL — where a browser tool's screenshot lands; verified live against 1.18.32, where the built-in `read` tool on an image file produces one too, re-encoded by opencode itself when large). **ACP:** `tool_call`/`tool_call_update` content items `{type:"content", content:{type:"image", data, mimeType}}` (verified live against `opencode acp`); a later update that repeats the call without content keeps the images.
- `file` `{mime, filename?, url?}`
- `subtask` `{sessionId?, description?, agent?}` (a subagent spawn)
- `compaction` `{auto: bool}` — a marker part on the assistant message that summarized the session (opencode: `CompactionPart`, verified against 1.18.31's `GET /doc`; carried as an ordinary part on `message.part.updated`/the transcript, not a separate event kind). `auto` distinguishes opencode's own context-overflow trigger from a person's "Compact now". opencode's OpenAPI also has richer `session.next.compaction.{started,delta,ended}`/`session.compacted` broadcast events (progress text, `reason: auto|manual`) that this backend does not map — the `compaction` part is the single signal Cerea needs, per §8.

The agent is subscribed to its backend from process start, so it has seen every event of every session touched since; for sessions untouched since start, the backend's persisted transcript is exact. The snapshot therefore equals "persisted transcript + everything applied since", with no gap.

**Questions and the generic tool part.** A question call also rides an ordinary `tool` part (`tool:"question"`, `status: pending→running→completed|error`, `input` carrying the same `questions` array) — the same double-reporting `permission.asked` already has alongside a tool part, and for the same reason: the transcript's own tool-call rendering keeps working even for a client that does not special-case questions, while `question.asked`/`question.resolved` are what the approval card actually answers through.

**Usage on `Session` (`session.get`/`session.list`).** opencode's own session object carries no usage field — only assistant messages do — so the agent caches each session's latest `Usage` as it is observed on the event stream (or when `Transcript` is fetched) and answers `session.get`/`session.list` from that cache. A session this process has not touched since it started (no event, no `Transcript` call) answers with `usage: null`; the caller's `session.sync` snapshot (which does read the persisted transcript) is what backfills that case, per the no-gap guarantee above.

## 8. Cerea side (what maps to what)

- The browser-facing API is `/api/v2/code/v1/...?device=` plus `/api/v2/code/agents/[id]/stream`. Behind it, the forwarder (`src/routes/api/v2/code/[...path]/+server.ts`) maps each allowed path to one typed op on the device's `MachineLink` (`src/lib/server/code/machines.ts`), sent over the machine's socket.
- SSE bridge: register a fan-out listener (buffering), `session.sync` with the browser's `Last-Event-ID` (`<epoch>:<seq>`), emit (snapshot → chat frames, or the missing events), then drain buffered live events with `seq >` the sync's `seq`. SSE `id` = `<epoch>:<seq>` of the last envelope a frame came from. Epoch change → a `reset` event that makes the client re-fold from scratch. No per-frame info logs (R6).
- Mapping normalized → chat `AgentStreamUpdate` (`src/lib/server/code/machineTimeline.ts`): user `text` part (non-synthetic) → `user`; assistant `text` part/delta → `Stream`; `reasoning` part/delta → `Stream` wrapped in `<think>…</think>` (the chat's own reasoning shape, so `ChatMessage` shows its collapsible Thinking block; a delta is routed by the type its `part` event announced, and one that precedes its part is held until it arrives); `tool` part → Tool call / result / error (uuid = callId); `permission.asked/replied` → Elicitation request/resolved; `question.asked/resolved` → the same Elicitation request/resolved (the user-question tool design: normalized questions become `ElicitationField[]`, the same shape and card — `AskQuestion.svelte` — chat's own `ask_user_question` already uses); `status busy` → TurnState running, `idle` → done (failed if the last assistant message carries `error`); `error` → TurnState failed; `todo` → Plan; `usage` → a side-channel frame (M3).

**Tool-output images.** A completed `tool` part's `attachments` map, in the same function for a snapshot and a live event, to a second entry in the result frame's `outputs`: `{content: [{type:"image", mimeType, url}]}`, where `url` is `<base>/api/v2/code/v1/agents/<sessionId>/attachments/<sha256>?device=<id>` — the forwarder's raw route below — beside the `data:` images an MCP tool's result already carried (`ToolUpdate.svelte` renders both; a `url` is loaded only if it is a same-origin path). Cerea keeps only well-formed entries (64-hex sha, raster mime, 0 < size ≤ 8 MiB) and at most 8 per call, and appends a text output ("N images not shown …") for `attachmentsOmitted` plus any entry it dropped. `ToolUpdate.svelte` loads a `url` only if it is exactly this route's URL (`…/agents/<id>/attachments/<64 hex>?device=<24 hex>`), never any other path. Bytes never ride the stream, and **nothing is persisted in Cerea**: no image, no url, no capability at rest — the machine is asked again on every view and the browser caches the answer.

`GET /api/v2/code/v1/agents/:id/attachments/:sha256?device=` (the forwarder's raw route; `:sha256` must be 64 lowercase hex) calls `session.attachment`. It has the forwarder's usual authorization (§4: the signed-in person, their paired device, the machine's live link); the sha in the URL is **not** a capability — the op answers only for that session's own images. Because the machine is untrusted (a compromised one is assumed possible), Cerea judges the _bytes_, not the machine's word:

- the type comes from the **magic numbers** against the raster allowlist (PNG, JPEG, GIF, WebP) and the claimed `mime` is ignored — a PNG labelled `text/html` is served as `image/png`, SVG/HTML/text labelled `image/png` is `415`;
- width × height is read from the header (PNG IHDR, the JPEG frame header, GIF, all three WebP variants); more than **50 megapixels**, zero, or a header that cannot be read is `413` — a decompression bomb is a few dozen bytes;
- more than **8 MiB** is `413`, checked on the base64 length before decoding;
- the bytes must hash to the requested sha, else `502` (this is what makes the caching below sound);
- the response is `Content-Type` from the bytes, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cache-Control: private, max-age=31536000, immutable` (keyed by sha; private because a shared cache must not keep a person's screenshots);
- machine answers map as elsewhere: `not_found` (unknown, or "no longer on the machine") and `unsupported` are `404`; a view is audited (`attachment.raw`, session/sha and byte count, never content).

Known limit: a broken image is what a person sees for an image the machine no longer has (ACP after a galopin restart, or an opencode session whose history was compacted away); the 404 body names why.

## 9. Machine powers: files and terminals (specified by ADR 0090; F1 and T1 build it)

**Implemented:** `files.list`, `files.stat`, `files.read` and `files.status`; the `files` and `fileDeny` policy fields with `enroll --no-files`, `--file-deny GLOB` and `--no-default-file-deny`; every `terminal.*` op, the binary frames and flow control (§9.2), with the `terminal` and `maxTerminals` policy fields. `hello.machine.capabilities` reports `files: true`, `terminal` where the OS supports it, and `fileSearch`, `fileWatch` and `fileWrite` false. The error codes `conflict` and `too_large` are in both halves. **Specified, not built:** `files.find`, `files.grep`, `files.watch`, `files.unwatch` and `files.write` (they answer `unsupported`), the `fileWrite` policy field and `CODE_FILE_WRITE_ENABLED`.

Additive only: `protocol` stays `1`. Everything here exists only when `hello.machine.capabilities` says so, and an unknown op still answers `unsupported`, so an old Cerea paired with a new galopin works unchanged, and so does the reverse. These are **machine ops**: galopin dispatches `files.*` and `terminal.*` before the backend switch, and they never call opencode or an ACP agent. opencode's own `/file*`, `/find*` and `/pty` are deliberately not used.

A power is live only when the machine policy (§4), the deployment switch (`CODE_FILES_ENABLED`, `CODE_FILE_WRITE_ENABLED`, `CODE_TERMINAL_ENABLED`) and the capability all allow it. Cerea checks the first two before forwarding, answering 403 with the exact enroll flag, and galopin enforces the policy again.

### 9.1 Paths and confinement

- Paths are **workspace-relative**, `/`-separated, with no leading `/` and no `..` segments (`invalid` otherwise). `"."` is the root.
- Every access goes through Go's `os.Root` for the workspace (openat-based, so no TOCTOU). A symlink whose target escapes the root is listed with `escapes: true` and never followed or read.
- `.git/` is skipped. Dotfiles are listed with `hidden: true`. `fileDeny` matches are redacted.

### 9.2 Binary frames (terminal streams only)

galopin sends these only on a channel Cerea opened with `terminal.attach`, so a peer that does not know them never receives one.

```
byte 0        kind   0x01 term.output (M→C) · 0x02 term.input (C→M) · 0x03 term.ack (C→M)
byte 1        L      channel id length, 1..32
bytes 2..L+1  channel id, ASCII [A-Za-z0-9_-] (chosen by Cerea in terminal.attach, one per viewer)
next 8 bytes  u64 big-endian offset
                term.output: absolute output offset of the payload's first byte
                term.ack:    the viewer has consumed output up to (excluding) this offset
                term.input:  0
rest          payload: raw bytes. term.output ≤ 32 KiB; term.input ≤ 16 KiB; term.ack empty
```

Unknown kinds are ignored. Offsets are per terminal, start at 0 when it is spawned, and never reset for its life. Terminals die with the galopin process.

**Flow control:**

- galopin's writer has two lanes. Control (`res`, `event`, `notice`, `credential`, `auth`) is always drained before stream frames, which are at most 32 KiB each.
- Per channel, galopin sends output only while `sent − acked ≤ 256 KiB`. Acks come from the browser, after xterm has processed each 64 KiB, and Cerea relays them.
- Out of credit, galopin stops reading that PTY. With no viewer attached, or every viewer out of credit for 10 s, it keeps reading into its 2 MiB ring and drops the oldest bytes.
- A viewer that comes back behind the ring start gets `reset`.

- All terminals are closed on `run` shutdown and on a 4403 revoke.

### 9.4 Default `fileDeny`

`.env` · `.env.*` except `.env.example`, `.env.sample` and `.env.template` · `.envrc` · `*.pem` · `*.key` · `*.p12` · `*.pfx` · `*.kdbx` · `id_rsa*`, `id_ecdsa*`, `id_ed25519*` · `.netrc` · `.npmrc` · `.pypirc` · `.git-credentials` · `.aws/credentials` · `.docker/config.json` · `*.tfstate` · `secrets.y*ml`.

The deny list prevents **accidental** exposure: screen sharing, and content flowing through Cerea into logs or caches. It is **not** a security boundary once a terminal or the agent can read the file, and the UI says so.

### 9.5 Notices

`{"type":"notice","scope":{"workspaceId"?:"…","terminalId"?:"…"},"event":Notice}` frames are machine-level and lossy: no epoch or seq, no replay. A receiver that might have missed some re-queries `files.status` or `terminal.list`. `files.changed` is debounced to 200 ms with at most 256 paths; beyond that it carries `overflow: true`, and the receiver refreshes everything.

### 9.6 Browser side (Cerea)

- **Files:** REST on the forwarder, with the same `getPairedDevice` check. `conflict` maps to 409, `too_large` to 413, and `unsupported` to 404. The raw route serves only raster images inline, with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`. Anything else goes as `text/plain` or an attachment, never as HTML or SVG.
- **Terminal:** a browser WebSocket.
  1. `POST …/terminals/:id/ticket` passes through the hooks and returns a single-use ticket: 256 bits, 30 s, bound to user, session, device and terminal.
  2. Minting requires an OIDC `auth_time` within 12 h (otherwise re-login), plus the one-time acknowledgement per machine.
  3. The upgrade at `${base}/api/v2/code/terminal?ticket=…` redeems the ticket and requires `Origin` to equal the public origin.
  4. The socket re-checks the session and the device every 60 s and closes with 4403 on logout, revoke or unpair.
- **Audit:** Cerea `codeAudit` (90-day TTL) and galopin's local `audit.log` record actions (terminal open, attach and close; file writes; refusals; ticket failures). They never record keystrokes, output or file content.
